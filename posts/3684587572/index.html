1、pod是什么

pod是kubernetes中的最小调度单元，一个Pod封装一个容器（也可以封装多个容器），Pod里的容器共享存储、网络等。（pod一般运行在工作节点上）

【豌豆：豌豆是pod，豌豆荚中有1个/多个豌豆（即容器）】

⭐ pod是什么服务，取决于是什么镜像（例如下面的镜像是nginx,则pod服务大概率就是nginx）

pod:

container:

images：nginx

⭐ 可以将pod看作虚拟机，然后每个容器相当于运行在虚拟机的进程。

⭐ pod是需要调度到k8s集群的工作节点（node节点）来运行的，具体调度到哪个节点上,是根据scheduler调度器实现的

1.1 Pod如何管理多个容器？

1）特点：pod底下一般运行一个容器，也可以运行多个，但这种是当多个容器需要紧密配合时才会用，pod中的多个容器会被同时调度，并且共享网络资源，共享各种配置等。

2）使用场景：容器间需要密切配合时会用

Web服务器 + Sidecar容器：主容器（web）运行服务，辅助容器负责资源更新

共享存储：多个容器访问同一volume

3) 容器类型：pod下会有初始化容器（[Init容器]{.mark}）和主容器（应用容器）

1.2 Pod网络

1.2.1 Pod IP地址分配

独立IP：每个Pod都有唯一的IP地址

网络插件：由Calico、Flannel、Weave等网络插件划分IP段

虚拟网络：不共享物理机IP，运行在虚拟网络环境中

1.2.2 Docker容器网络共享（pod中多个容器时，网络需要共享）

方式：之前docker网络的其中一种，container模式（将不同容器的IP设置为一致）——参数：–net=container

[root@localhost _data]# docker run -itd –name 容器名2 –net=container:容器名1 centos

1.2.3 Kubernetes网络共享机制

[核心组件：Pause[pɔːz] 容器]{.mark}

启动顺序：先启动pause容器，再启动其他容器

网络共享：所有容器连接到pause容器实现网络共享 （可以理解为都读了pause容器的网络信息，以此实现共享）

统一IP：Pod内所有容器共享同一个IP和端口空间

1.3 Pod存储

[核心：]{.mark}volume共享存储

创建Pod的时候可以指定挂载的存储卷。 POD中的所有容器都可以访问共享卷，允许这些容器共享数据。 Pod只要挂载持久化数据卷，Pod重启之后数据就会存在。

2、之前学习过容器，为什么还需要Pod？

更高抽象：Pod是容器的集合，承载1个或多个容器，统一作为调度单位。

同调度同节点：Pod内容器被一致调度，必在同一节点运行，便于协作。

共享环境：

共享网络：同一IP与端口，容器间可用localhost直连，但需避免端口冲突。

共享存储：可挂载相同Volume，容器通过文件系统高效交换数据。

协作模式：适合需要紧密配合的多容器协作（如主应用+Sidecar），通过共享Network Namespace与Volume提升集成与性能。

K8s特性契合：以Pod为最小调度与管理单元，方便应用级伸缩、滚动更新、探针与策略统一管理。

⭐[一句话：容器解决“运行环境”，Pod解决“协作与调度边界”。]{.mark}

2.1 代码自动发版更新

思路：同个pod中，主容器运行应用；Sidecar 容器（辅助容器）运行“Git 同步服务”，定时拉取仓库最新代码；二者通过共享 Volume（代码目录）实现热更新/重载。

2.2 收集业务日志（Sidecar 日志容器）总结

思路：主业务容器只产生日志（只生成日志）；Sidecar 日志容器（辅助容器）负责采集并发送到日志服务器。两者通过共享日志目录实现解耦，不影响主业务生产日志。

⭐ pod 创建全流程（4 步记忆版）

1) 客户端提交：kubectl 命令向 apiserver 提交创建pod的请求，apiserver接收到pod创建请求后，会将pod的属性信息(metadata)写入etcd。

2）调度绑定：apiserver（触发watch）创建pod的信息转发给调度器scheduler，调度器使用调度算法选择node，将node信息返回给apiserver，apiserver将绑定的node信息写入etcd（记录pod绑定了哪个node信息）

3）真实创建：apiserver调用kubectl，指定pod信息，调用容器运行时创建并启用pod内的容器（含Calico分配网络、拉取镜像、创建pause）

4)状态回传：kubelet 上报状态 → apiserver → 写入 etcd，对外可见

❗ 口诀：API Server 通知，Scheduler 选人，Kubelet 干活，状态入 etcd

4.2  通过资源清单文件创建第一个Pod

pod下的字段 （一级字段，yaml中顶格写）

⭐书写的一些总结：

[root@node1 ~]# kubectl explain pod/资源控制器

1）<map[string]string> → 这种书写表示： key: values

例如：（metadata底下经常跟labels）

labels:

app: nginx-deploy

2）<string> → 直接跟字符串（例如：name: nginx-test）

3）<ObjectMeta> → 对象，说明底下有多个字符串

4）<×××> -required- → 后面跟了个required（必须），说明这是个必须要写的字段

5) <[]Container> -required- → 前面有个[]的，底下字段要以”-“开头,无需空两格

例如：（spec底下经常跟containers）

spec:

containers:

  • name: my-nginx

image: xianchao/nginx:v1

imagePullPolicy: IfNotPresent

1）自主式pod：创建第一个pod

[root@master1 pod_study]# cat first.yaml

+———————————————————————————————————————————–+
| Pod 资源清单字段总览 |
| |
| apiVersion: 资源所用的 API 版本（如 v1）。服务端会做版本转换；不认识的版本会被拒绝。 |
| |
| kind: 资源类型，Pod 固定为 Pod。 |
| |
| metadata: 元数据，描述对象的身份与标签等。 |
| |
| spec: 期望状态/规格，描述 Pod 行为（容器、网络、调度等）。 |
| |
| status: 实际状态，由系统填充，只读；无需在清单中编写。 |
| |
| metadata 常见字段 |
| |
| name: 资源名。命名空间内唯一。 |
| |
| namespace: 命名空间；不写等价于 default。 |
| |
| labels** (map[string]string): 标签，用于选择器与分类，如 app: tomcat。 |
| |
| annotations (map[string]string): 注解，存放非结构化信息（构建/发布信息、镜像 hash、联系方式、监控配置等），不可用于选择器。 |
| |
| 其他较少直接手写的字段（了解即可）： |
| |
| generateName（由系统基于前缀生成随机名）、uid、resourceVersion、creationTimestamp、ownerReferences、clusterName 等。 |
| |
| spec 核心字段与含义 |
| |
| containers (必填，[]Object): 容器列表，至少一个(要“-”起)。部署后不能增删，仅重建可变更。 |
| |
| name (必填): 容器名。 |
| |
| image: 镜像（如 xianchao/tomcat-8.5-jre8:v1）。 |
| |
| imagePullPolicy: 镜像拉取策略 |
| |
| Always: 总是拉取（配合 :latest 常见）。 |
| |
| IfNotPresent: 本地有则用本地，否则拉取（默认行为，除非 tag 为 latest）。 |
| |
| Never: 从不拉取（完全依赖本地）。 |
| |
| ports ([]Object): 容器端口声明（主要用于标注，非必填；不写不影响端口实际监听）。 |
| |
| env / envFrom: 环境变量；从字面量、ConfigMap、Secret 注入。 |
| |
| command / args: 入口命令与参数（覆盖镜像中 ENTRYPOINT/CMD）。 |
| |
| resources: 资源请求/限制（requests/limits 的 CPU/内存）。 |
| |
| livenessProbe / readinessProbe / startupProbe: 存活/就绪/启动探针。 |
| |
| volumeMounts / volumeDevices: 挂载卷或块设备。 |
| |
| securityContext: 容器级安全上下文（UID/GID、只读根文件系统、能力等）。 |
| |
| 其他：workingDir、stdin、tty、lifecycle、terminationMessagePath/Policy。 |
| |
| 调度与网络/主机相关： |
| |
| nodeName: 直接指定节点名（强绑定）。 |
| |
| nodeSelector (map[string]string)、affinity: 基于标签/规则的调度约束。 |
| |
| tolerations: 容忍污点，用于允许调度至有污点的节点。 |
| |
| hostNetwork/hostPID/hostIPC (bool): 是否共享宿主机网络/PID/IPC 命名空间。 |
| |
| dnsPolicy/dnsConfig: DNS 策略与自定义解析。 |
| |
| hostname/subdomain/setHostnameAsFQDN: Pod 主机名及 FQDN 设置。 |
| |
| 服务账号与安全： |
| |
| serviceAccount / serviceAccountName**: 所用 ServiceAccount。 |
| |
| automountServiceAccountToken: 是否自动挂载 SA Token。 |
| |
| securityContext (Pod 级): Pod 级别安全设置（与容器级叠加）。 |
| |
| runtimeClassName: 容器运行时类（如 gVisor、Kata）。 |
| |
| 启停与生命周期： |
| |
| restartPolicy: 重启策略（Always/OnFailure/Never），Pod 级；单 Pod 常见 Always。 |
| |
| terminationGracePeriodSeconds: 优雅终止等待秒数（向容器发 SIGTERM，超时后 SIGKILL）。 |
| |
| activeDeadlineSeconds: Pod 最长存活时间，超时后终止。 |
| |
| initContainers: 初始化容器（串行先行执行，全部成功后主容器启动）。 |
| |
| ephemeralContainers: 临时调试容器（排障用，不参与常规生命周期）。 |
| |
| 存储： |
| |
| volumes: 卷定义（emptyDir、hostPath、configMap、secret、persistentVolumeClaim 等）。 |
| |
| 其他调度/控制： |
| |
| schedulerName: 指定调度器。 |
| |
| priority / priorityClassName: 优先级与优先级类。 |
| |
| preemptionPolicy: 抢占策略。 |
| |
| topologySpreadConstraints: 拓扑分布约束，打散副本。 |
| |
| readinessGates: 基于额外条件决定 Pod 就绪。 |
| |
| enableServiceLinks: 是否注入 Service 环境变量。 |
| |
| imagePullSecrets: 私有仓库拉取凭据。 |
| |
| overhead: 运行时开销（用于资源会计/调度）。 |
| |
| containers.ports 字段详解（每个元素是一个端口对象） |
| |
| containerPort (必填, int): 容器监听端口（0 < x < 65536）。 |
| |
| protocol (string): TCP（默认）/UDP/SCTP。 |
| |
| name (string): 端口名，同一 Pod 内唯一；Service 选择 targetPort 时可用名字匹配。 |
| |
| hostPort (int): 将容器端口映射到宿主机端口；慎用（影响调度、端口冲突）。 |
| |
| hostIP (string): 指定绑定宿主机的 IP（配合 hostPort）。 |
| |
| 说明：ports 更多是“声明/标注”，不声明也不会阻止应用在容器内监听端口；实际对外访问通常通过 Service 暴露，而非 hostPort。 |
| |
| ⭐kubectl explain 使用要点 |
| |
| kubectl explain pod：看整体结构与字段分层。 |
| |
| kubectl explain pod.metadata、kubectl explain pod.spec：逐层查看对象字段。 |
| |
| kubectl explain pod.spec.containers、…containers.ports：深入容器与端口字段。 |
| |
| 可加 –recursive 查看完整层级结构。 |
| |
| ⭐实用编写建议 |
| |
| 优先使用 labels 做选择器与分类，annotations 存放非结构化运维信息。 |
| |
| 避免随意使用 hostPort/hostNetwork；对外暴露请优先使用 Service/Ingress。 |
| |
| 合理设置 resources 与 probes，保证稳定性与可观测性。 |
| |
| 镜像标签尽量使用不可变版本（避免 latest），并与合适的 imagePullPolicy 搭配。 |
| |
| 使用 initContainers 做预热/依赖检查/权限准备，主容器更纯粹。 |
| |
| 私有仓库镜像需配置 imagePullSecrets。 |
| |
| 需要跨可用区/主机打散时配置 topologySpreadConstraints。 |

⭐故障排查：calico（网络插件）问题的解决方法

报错信息：…. plugin type=”calico” failed (add): error getting ClusterInformation: connection is unauthorized: Unauthorized

解决方法：

1、master节点上卸载calico: kubectl delete -f calico.yaml

2、重建calico：kubectl apply -f calico.yaml

systemctl stop kubelet

systemctl restart containerd # docker/containerd/crio

rm -rf /var/lib/cni/* # 清理 CNI 状态

rm -rf /var/lib/[网络插件]/* # 清理网络插件缓存

rm -rf /opt/cni/bin/*

systemctl start kubelet
