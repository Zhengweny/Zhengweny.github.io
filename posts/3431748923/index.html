Pod生命周期-启动钩子、停止钩子

发表于2026-05-07|更新于2026-05-07|学习类云原生Pod
|总字数:4.6k|阅读时长:21分钟|浏览量:

一、Pod 生命周期概念

1. 生命周期概述

Pod生命周期：从创建到终止的完整过程，包含多个重要阶段和组件。

2. Pod 状态概念

状态 含义 简单理解

Pending 等待调度 已创建但还没找到合适的节点

ContainerCreating 创建容器 正在拉取镜像和创建容器

Running 正常运行 所有容器都启动成功

Succeeded 成功完成 任务正常结束，不会重启

Failed 执行失败 任务异常结束，可能重启

Unknown 状态未知 无法获取状态信息

3. 生命周期重要组件

3.1 基础容器（Pause）

+———————————————————————–+
| 作用：为 Pod 提供共享的网络和存储空间 |
| |
| 特点：所有容器都”住”在这个基础容器里 |
| |
| (相当于一个基底，类比一台硬件，各种东西的存在都基于硬件) |
| |
| 自动创建：不需要手动配置 |
+———————————————————————–+

3.2 初始化容器（Init Containers）

+———————————————————————–+
| 作用：在主容器启动前做准备工作（主容器就是你准备创建的容器） |
| |
| 特点：按顺序执行，全部完成后才启动主容器 |
| |
| 用途：下载文件、等待依赖服务、初始化数据库等 |
+———————————————————————–+

3.3 生命周期钩子

+———————————————————————–+
| postStart：主容器启动后执行（如复制文件） |
| |
| preStop：主容器停止前执行（如通知监控） |
| |
| 特点：针对每个容器，不是整个 Pod |
+———————————————————————–+

3.4 健康检查探针

+————————————————————————————————————————————+
| startupProbe（启动探针）：启动时检查，[容器是否真正启动成功，]{.mark}成功后不再执行 （必须先检查，后面两个检查则是并行的） |
| |
| livenessProbe（存活性探针）：存活性检查，检测[容器进程是否还活着，]{.mark}失败时重启容器 |
| |
| readinessProbe（就绪性探针）：就绪性检查，检测[容器服务是否正常，]{.mark}失败时从服务中移除 |
+————————————————————————————————————————————+

3.4.1 探针[三种检查方式：]{.mark}

+———————————————————————–+
| exec：执行命令检查 |
| |
| tcpSocket：检查端口连接 |
| |
| httpGet：发送 HTTP 请求检查 |
+———————————————————————–+

3.5 重启策略

+———————————————————————–+
| Always：任何退出都重启（默认） |
| |
| OnFailure：只有异常退出才重启（推荐） |
| |
| Never：从不重启 |
+———————————————————————–+

4. Pod 终止过程概念

+———————————————————————————————————————————+
| 用户删除：发出删除命令：kubectl delete pods ，kubectl delete -f yaml |
| |
| 宽限期：默认 30 秒等待时间 |
| |
| 标记终止：Pod 状态变为 Terminating |
| |
| 启动关闭：同时进行多个操作 (例如下面的[移除 Endpoints、执行 preStop 钩子、发送 TERM 信号这些相关的关闭操作是同时进行的]{.mark}) |
| |
| 移除服务：从 Service 中移除：endpoints 控制器监控到 pod 对象关闭，将pod与service匹配的 endpoints 列表中删除 |
| |
| 执行钩子：运行 preStop 钩子 |
| |
| 发送信号：给容器发送终止信号 |
| |
| 强制终止：宽限期结束后强制杀死 |
| |
| 完成删除：从系统中彻底删除 |
+———————————————————————————————————————————+

** 二、Init 容器（初始化容器）**

1、核心概念

+———————————————————————–+
| 作用：在主容器启动前做初始化工作 |
| |
| 执行顺序：按定义顺序依次执行，全部完成后才启动主容器 |
| |
| 存储共享：与主容器共享存储卷，数据可以传递 |
| |
| 不支持：readinessProbe（就绪探测）【探测容器服务的，主容器才有】 |
+———————————————————————–+

2、基础使用案例

案例1：等待依赖服务（会一直循环）

[root@master1 pod_study]# cat init-wait-service.yaml

apiVersion: v1

kind: Pod

metadata:

name: myapp-pod

labels:

app: myapp

spec:

initContainers:

  • image: busybox:1.28

imagePullPolicy: IfNotPresent

name: init-myservice

command:

  • ‘sh’

  • ‘-c’

  • ‘until nslookup myservice.$(cat /var/run/secrets/kubernetes.io/serviceaccount/namespace).svc.cluster.local; do echo waiting for myservice; sleep 2; done’

  • name: init-mydb

image: busybox:1.28

imagePullPolicy: IfNotPresent

command:

  • ‘sh’

  • ‘-c’

  • ‘until nslookup mydb.$(cat /var/run/secrets/kubernetes.io/serviceaccount/namespace).svc.cluster.local; do echo waiting for mydb; sleep 2; done’

containers:

  • name: myapp-container

image: busybox:1.28

imagePullPolicy: IfNotPresent

command:

  • ‘sh’

  • ‘-c’

  • ‘echo The app is running! && sleep 3600’

⭐注意：这个例子中有两个初始化容器：init-myservice和init-mydb

对应的命令是每 2 秒重试一次until 循环，去尝试解析nslookup服务名，但在已有的服务中不存在myservice和mydb供解析，所以初始化容器找不到就会一直重试

[root@master1 ~]# kubectl get pods -w

NAME READY STATUS RESTARTS AGE

myapp-pod 0/1 Init:0/2 0 9s

⭐任何一个初始化容器失败都会阻塞主容器启动

⭐ 实验目的及总结

示例中的场景：​初始化容器准备文件，主容器使用文件。

1、确保spec下，共享卷为空

spec:

volumes:

  • name: workdir # 定义卷名称

emptyDir: {} # 创建空目录作为共享存储

2、初始化容器准备文件挂载到共享卷名为workdir下，挂载目录可以自定义

spec:

initContainers:

volumeMounts:

  • name: workdir # 挂载共享卷

mountPath: /work-dir

3、主容器使用初始化准备的文件，因此挂载在同一共享卷workdir下，挂载目录同样可以自定义，但是读的就是同一个文件了。

spec:

containers:

volumeMounts:

  • name: workdir # 挂载同一个共享卷

mountPath: /usr/share/nginx/html

⭐​数据共享​：不同路径访问的是同一份文件系统！

注：关于volumes下的emptyDir

卷emptyDir最初是空的，Pod中的所有容器都可以读写emptyDir卷中的文件，尽管该卷可以在每个容器中挂载到相同或不同的路径。即使容器崩溃，卷中的数据emptyDir仍然是安全的。

三、主容器生命周期钩子

1、钩子类型对比

钩子类型 执行时机 用途 失败后果

postStart 容器启动后立即执行 资源部署、环境准备 杀死容器，根据重启策略决定

preStop 容器删除前执行 优雅关闭、释放资源 继续删除流程

2、基础钩子示例

[案例4：基础生命周期钩子]{.mark}

[root@master1 pod_study]# cat lifecycle-basic.yaml

apiVersion: v1

kind: Pod

metadata:

name: life-demo

labels:

app: life-demo

spec:

containers:

  • name: lifecycle-demo-container

image: xianchao/nginx:v1

imagePullPolicy: IfNotPresent

ports:

  • containerPort: 80

lifecycle:

postStart: # 启动钩子：容器runnin后马上执行

exec:

command:

  • ‘sh’

  • ‘-c’

  • ‘echo “lifecycle hookshandler” > /usr/share/nginx/html/test.html’

preStop: # 停止钩子，容器删除前执行

exec:

command:

  • ‘sh’

  • ‘-c’

  • ‘echo “PreStop hook is executing” > /proc/1/fd/1 && sleep 10 && nginx -s stop’

# 我们echo一句话到日志，看日志的时候才能明显看到preStop钩子确实会在pod彻底结束前执行

3、生产环境钩子示例

[案例5：Java 应用钩子]{.mark}

# 文件名: lifecycle-java.yaml

apiVersion: v1

kind: Pod

metadata:

  name: java-app

  labels:

    app: java

spec:

  containers:

  - name: war

    image: sample:v2

    imagePullPolicy: IfNotPresent

    ports:

    - containerPort: 8080

    lifecycle: # 生命周期

      postStart:

        exec: # 用exec一般后面就是接command命令

          command:

          - “cp”

          - “/sample.war”

          - “/app”

      preStop:

        httpGet: # 发送http

          host: monitor.com

          path: /warning

          port: 8080

          scheme: HTTP

注意⭐：

以上示例中，定义了一个Pod，包含一个JAVA的web应用容器，其中设置了PostStart和PreStop回调函数。即在容器创建成功后，复制/sample.war到/app文件夹中。而在容器终止之前，发送HTTP请求到http://monitor.com:8080/waring，即向监控系统发送警告。

4、优雅删除资源对象

方式1：默认方式（SIGTERM 信号）

删除流程：

1. 用户执行 kubectl delete pod

2. K8S 发送 SIGTERM 信号给容器中 PID=1 的进程

3. 等待 30 秒（默认宽限期）

4. 如果进程未退出，发送 SIGKILL 信号强制杀死

特点：

1、简单，不需要额外配置

2、依赖应用程序正确处理 SIGTERM 信号

3、如果应用不处理 SIGTERM，会被强制杀死

方式2：使用 preStop 钩子（应用程序很可能不处理SIGTERM信号，导致被强制杀死，因此就常用钩子来优雅停止应用）

删除流程：

1. 用户执行 kubectl delete pod

2. 执行 preStop 钩子（在发送 SIGTERM 之前） → 这个时候一般就是进行优雅停止

3. 等待 preStop 执行完成

4. 发送 SIGTERM 信号

5. 等待宽限期结束

特点：

1、更精确的控制

2、可以在发送信号前做清理工作

3、适合需要特殊关闭流程的应用

注意：2、基础钩子示例（案例4中的nginx就是在优雅停止nginx）

四、 完整生命周期示例

[案例7：完整生命周期示例]{.mark}

# 文件名: complete-lifecycle.yaml

apiVersion: v1

kind: Pod

metadata:

name: complete-demo

labels:

app: complete

spec:

restartPolicy: OnFailure

terminationGracePeriodSeconds: 60

# 初始化容器

initContainers:

  • name: init-setup

image: busybox:1.28

imagePullPolicy: IfNotPresent

command: [‘sh’, ‘-c’, ‘echo “Init container setup completed”‘]

# 主容器

containers:

  • name: nginx

image: nginx:latest

imagePullPolicy: IfNotPresent

ports:

  • containerPort: 80

# 生命周期钩子

lifecycle:

postStart: # 容器启动后马上执行

exec:

command: [‘/bin/sh’, ‘-c’, ‘echo “Container started at $(date)” > /tmp/start.log’]

preStop: # 容器停止前执行

exec:

command: [‘/bin/sh’, ‘-c’, ‘echo “Container stopping at $(date)” > /tmp/stop.log’]

# 健康检查

startupProbe: # 启动探测

httpGet:

path: /

port: 80

initialDelaySeconds: 10

periodSeconds: 5

failureThreshold: 3

livenessProbe: # 存活探测

httpGet:

path: /

port: 80

initialDelaySeconds: 30

periodSeconds: 10

failureThreshold: 3

readinessProbe: # 就绪探测

httpGet:

path: /

port: 80

initialDelaySeconds: 5

periodSeconds: 5

failureThreshold: 3

[⭐总结]{.mark}

pod在整个生命周期中有非常多的用户行为：

1、初始化容器完成初始化

2、主容器启动后可以做启动后钩子（postStart）

3、主容器结束前可以做结束前钩子 (preStop)

4、在主容器运行中可以做一些健康检测（探测），如startupprobe、livenessprobe，readnessprobe
