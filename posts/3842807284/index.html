1、标签管理

1.1 什么是标签？

+—————————————————————————–+
| 标签是键值对（key/value），用于标识和分类Kubernetes对象。标签帮助我们： |
| |
| - 快速识别Pod的用途 |
| |
| - 按版本、环境等维度分组管理 |
| |
| - 支持选择器进行批量操作 |
+—————————————————————————–+

1.2 标签操作命令

1）给pod打标签

# 给已存在的Pod打标签（tomcat-test 为pod名）

kubectl label pods tomcat-test release=v1

# 查看该pod的所有标签

kubectl get pods tomcat-test –show-labels

2）查看标签

# 查看所有Pod的标签（最后一列就会展示lables）

[root@master1 ~]# kubectl get pods –show-labels

[root@master1 ~]# kubectl get pods -n kube-system –show-labels

# 按标签筛选Pod

2、节点选择器

+———————————————————————————————————————————————–+
| 创建pod资源时，pod会根据schduler进行调度，会默认随机调度到一个node上。 |
| |
| 但如果我们想要pod调度到指定节点或调度到一些具有相同特点的node节点上，则可以使用节点选择器，使用nodeName或nodeSelector字段指定要调度的node节点 |
+———————————————————————————————————————————————–+

3. Node 节点亲和性（nodeAffinity）

[1）核心概念]{.mark}

[affinity (亲和性)[əˈfɪnəti]： 为 Pod 设置调度约束的规则集合。（就是说明怎么调度）]{.mark}

+———————————————————————–+
| nodeAffinity: Pod 与 Node 的匹配关系（本节重点） |
| |
| podAffinity: Pod 与 Pod 倾向在一起 |
| |
| podAntiAffinity: Pod 与 Pod 倾向分开 |
+———————————————————————–+

[2）两类 nodeAffinity]{.mark}

+————————————————————————————————————+
| requiredDuringSchedulingIgnoredDuringExecution（硬亲和性）: 必须满足才会调度，否则一直 Pending。 |
| |
| preferredDuringSchedulingIgnoredDuringExecution（软亲和性）: 尽量满足，不满足也可调度；可设置权重 weight。 |
+————————————————————————————————————+

[3）字段结构]{.mark}

# 编写结构如下：

spec

  affinity

    nodeAffinity

      requiredDuringSchedulingIgnoredDuringExecution          # 硬亲和性（Object）

        nodeSelectorTerms:                                    # 必填（Array），不同 term 之间是 OR

        - matchExpressions:                                   # AND 关系（推荐）

          - key: <string>                                     # 必填：节点标签键

            operator: In|NotIn|Exists|DoesNotExist|Gt|Lt      # 必填：操作符

            values: [<string>…]                             # 随 operator 不同而不同

          matchFields:                                        # AND 关系（少用）

          - key: <string>

            operator: In|NotIn|Exists|DoesNotExist|Gt|Lt

            values: [<string>…]

==========================================================================================

      preferredDuringSchedulingIgnoredDuringExecution         # 软亲和性（Array）

      - weight: <1..100>                                      # 权重，越大越优先

        preference:

          matchExpressions: […]

          matchFields:      […]

⭐ 关键字段说明

### requiredDuringSchedulingIgnoredDuringExecution（硬亲和性）

- 类型: Object

- 必须满足才可调度；否则 Pod 将 Pending

- 子字段：

  - nodeSelectorTerms: Array（必填） ⭐硬亲和性才有的字段，硬亲和性无权重 weight字段

    - 多个 term 之间“OR”（任意一个 term[就是数组] 满足即可）

### preferredDuringSchedulingIgnoredDuringExecution（软亲和性）

- 类型: Array

- 尽量匹配；不满足也能调度

- 子元素：

  - weight: 1~100（权重，越大越优先） ⭐ 软亲和性才有权重weight，无节点选择器nodeSelectorTerms

  - preference: 规则主体，包含 `matchExpressions`/`matchFields`

### matchExpressions（最常用）

单个表达式由以下字段组成：

- key（必填）: 节点标签的键

- operator（必填）: 取值规则如下 （In/NotIn/Exists/DoesNotExist/Gt/Lt）

- values（按 operator 要求填写）

operator[ˈɒpəreɪtə(r)] 与 values 约束：

- In / NotIn: values 必须非空（列表）

- Exists / DoesNotExist: values 必须为空（不写或空数组）

- Gt / Lt: values 只能有 1 个值，且按整数比较

⭐ 语义速记：

- In: 节点标签值在给定列表中

- NotIn: 节点标签值不在给定列表中

- Exists: 节点具有该标签键

- DoesNotExist: 节点不具有该标签键

- Gt/Lt: 节点标签值可被视为整数，做大小比较

⭐软亲和性和硬亲和性举例

#####硬亲和性

nodeSelectorTerms字段是or,matchExpressions字段是and

举例 1（硬亲和性 OR + AND）

目标：节点要么在 zone=foo（且disk=ssd），要么在 zone=bar（且disk=hdd）

requiredDuringSchedulingIgnoredDuringExecution:

  nodeSelectorTerms:           # 外层 OR：两组选其一，或的关系

  - matchExpressions:          # 第1组（AND），且的关系

    - {key: zone, operator: In, values: [“foo”]}

    - {key: disk, operator: In, values: [“ssd”]}

  - matchExpressions:          # 第2组（AND），且的关系

    - {key: zone, operator: In, values: [“bar”]}

    - {key: disk, operator: In, values: [“hdd”]}

注：满足第1组“zone=foo 且 disk=ssd”，或满足第2组“zone=bar 且 disk=hdd”，就能被调度。

#####软亲和性

目标：偏好 zone=foo（10 分），更偏好 disk=ssd（20 分）。权重问题

preferredDuringSchedulingIgnoredDuringExecution:

- weight: 10

  preference:

    matchExpressions:

    - {key: zone, operator: In, values: [“foo”]}

- weight: 20

  preference:

    matchExpressions:

    - {key: disk, operator: In, values: [“ssd”]}

注：

节点A zone=foo 权重为10分；节点B disk=ssd 权重为20；

则调度会更倾向于节点B

但两者都不满足也仍可以调度到其它节点（软约束）

⭐ 方便记忆

required：外层（nodeSelectorTerms）是“或者”、内层（matchExpressions）是“并且”，不满足就一直 Pending。

preferred：命中规则就加分，权重高者优先，但不是强制。

[4）node节点硬亲和性例子（]{.mark}requiredDuringSchedulingIgnoredDuringExecution[）]{.mark}

前提：先将pod镜像放到两个node节点上

# 导入镜像

[root@node1 pod_study]# ctr -n=k8s.io images import myapp-v1.tar.gz

# 查看镜像名

[root@node1 pod_study]# ctr -n=k8s.io images ls | grep myapp

docker.io/ikubernetes/myapp:v1

# 在master上模拟硬亲和性，如果满足zone=cool或zone=winter则能被调度

[root@master1 pod_study]# cat pod-require-affinity.yaml

apiVersion: v1

kind: Pod

metadata:

name: pod-require-affinity-demo

spec:

affinity:

nodeAffinity:

requiredDuringSchedulingIgnoredDuringExecution:

nodeSelectorTerms: # 硬亲和性才有，以下两组，即zone=cool和zone=winter必须满足一组才会能被调度

  • matchExpressions:

  • key: zone

operator: In

values:

  • cool

  • winter

containers:

  • name: myapp

image: ikubernetes/myapp:v1

# 此时，我什么标签都没建立，直接运行，会显示pending

[root@master1 pod_study]# kubectl apply -f pod-require-affinity.yaml

[root@master1 pod_study]# kubectl get pods

pod-require-affinity-demo 0/1 Pending 0 7s

# 我们按照要求，建立一个满足条件的标签（zone=cool或zone=winter）的node，则能看到pod正常运行

[root@master1 ~]# kubectl label node node1(node节点名) zone=cool

# 再次查看pod,pod就是running状态了

[root@master1 pod_study]# kubectl get pods

pod-require-affinity-demo 1/1 Running 0 2m18s

[5）node节点软亲和性例子]{.mark}

（preferredDuringSchedulingIgnoredDuringExecution）

# 在master上编写yaml模拟软亲和性，权重越大越倾向于调度，第一组是zone1=cool1/winter1(权重为10)，第二组是zone2=cool2/winter2（权重为20），如果双方标签都存在，则倾向于调度到zone2,因为权重更大

[root@master1 pod_study]# cat pod-perfer-affinity-demo.yaml

apiVersion: v1

kind: Pod

metadata:

name: pod-prefer-node-demo

spec:

affinity:

nodeAffinity:

preferredDuringSchedulingIgnoredDuringExecution:

  • preference:

matchExpressions:

  • key: zone1 # ⭐zone1=cool1/winter1（key-value是一对一的关系，一个key只能对应一个value值）

operator: In

values:

  • cool1

  • winter1

weight: 10

  • preference:

matchExpressions:

  • key: zone2

operator: In

values:

  • cool2

  • winter2

weight: 20

containers:

  • name: myapp

image: docker.io/ikubernetes/myapp:v1

imagePullPolicy: IfNotPresent

# ⭐目前我们什么标签都没有建立，运行pod并检查pod的状态是 Running，说明软亲核心是非常宽松的，即使标签都没有定义，也会随机调度到某一节点上

[root@master1 pod_study]# kubectl apply -f pod-perfer-affinity-demo.yaml

pod/pod-prefer-node-demo created

[root@master1 pod_study]# kubectl get pods -o wide

pod-prefer-node-demo 1/1 Running 0 29s 10.244.166.134 node1 <none> <none>

# 我们建立node2节点的标签为zone2=cool2再看看情况

[root@master1 pod_study]# kubectl label node node2 zone2=winter2

[root@master1 pod_study]# kubectl get pods -o wide | grep pre

pod-prefer-node-demo 1/1 Running 0 5m49s 10.244.166.135 node1 <none> <none>

⭐ 如上可见，此时还在node1，这说明一个问题，一旦Pod 被调度到某个节点，除非删除重建，否则不会因为节点标签变化而迁移（所以一般apply yaml建立pod前，我们就应该对应创建节点标签！！）

# 我们此时删除pod重建，建立node1的标签（权重小），观察到节点确实会在node2上

[root@master1 pod_study]# kubectl label node node1 zone1=winter1

[root@master1 pod_study]# kubectl delete -f pod-perfer-affinity-demo.yaml

pod “pod-prefer-node-demo” deleted

[root@master1 pod_study]# kubectl apply -f pod-perfer-affinity-demo.yaml

pod/pod-prefer-node-demo created

[root@master1 pod_study]# kubectl get pods -o wide | grep pre

pod-prefer-node-demo 0/1 ContainerCreating 0 4s <none> node2 <none> <none>

| |

| |
| Exists：标签存在 |
| |
| DoesNotExist：标签不存在 |

4. Pod 节点亲和性

1) 核心概念

⭐位置是关键，定义位置的是topologyKey

+—————————————————————————————————————+
| podAffinity（Pod 亲和性）: 新 Pod 倾向于与特定标签的 Pod 在同一个位置（如同一节点/同一机架/同一可用区）。 |
| |
| 适用场景：nginx + tomcat 部署在同一区域，提高通信效率。 |
| |
| podAntiAffinity（Pod 反亲和性）: 新 Pod 倾向于与特定标签的 Pod 不在同一个位置。 |
| |
| 适用场景：避免两套程序相互影响，提高容错性。 |
| |
| topologyKey（拓扑键）: 定义“位置”的标准。相同 topologyKey 值的节点被认为是同一位置。 |
| |
| 常用值：kubernetes.io/hostname（按节点名区分）、zone（按可用区标签区分）。 |
+—————————————————————————————————————+

2）字段结构（与 nodeAffinity 类似）

+———————————————————————–+
| 硬亲和性: requiredDuringSchedulingIgnoredDuringExecution |
| |
| 必须满足条件才能调度，否则 Pod 一直 Pending。 |
| |
| 软亲和性: preferredDuringSchedulingIgnoredDuringExecution |
| |
| 尽量满足条件，不满足也可调度；支持 weight 权重。 |
| |
| [关键字段：]{.mark} |
| |
| labelSelector: 选择作为亲和/反亲和对象的 Pod（通过标签匹配） |
| |
| namespaces: 指定查找 Pod 的命名空间（不写则默认为当前命名空间） |
| |
| topologyKey: 定义位置拓扑的键（必填） |
| |
| ⭐注意： |
| |
| 选择节点nide → nodeSelectorTerms（硬）或 preference（软） |
| |
| 选择 Pod → labelSelector（硬和软都用这个） |
+———————————————————————–+

3）Pod 硬亲和性例子

[目标：第二个 Pod 必须与第一个 Pod（标签 app2=myapp2）在同一节点。]{.mark}

# 第一个 Pod（基准）

[root@master1 pod_study]# cat pod-require-affinity.yaml

name: pod-affinity

containers:

  • image: docker.io/ikubernetes/myapp:v1

imagePullPolicy: IfNotPresent

name: myapp

# 此时检查下第一个pod的信息，可以看到被随机调度到node1上（⭐如果想指定节点位置，则在spec下指定nodeName: node2节点字段）

# 第二个 Pod（跟随第一个，做亲和性）

4）Pod 反亲和性例子 （硬亲和性）

[目标：第二个 Pod 必须与第一个 Pod（标签 app2=myapp2）不在同一节点。]{.mark}

# 保留第一个实验上面的pod-affinity，删除second-pod-require-affinity.yaml对应的容器

[root@master1 pod_study]# kubectl get pods -o wide # 目前可以看到pod-affinity是在node1

apiVersion: v1

kind: Pod

metadata:

name: second-pod-affinity

labels:

tier: backend

requiredDuringSchedulingIgnoredDuringExecution:

  • labelSelector:

matchExpressions:

  • key: app2

operator: In

values:

  • myapp2

topologyKey: kubernetes.io/hostname

containers:

  • image: docker.io/library/busybox:1.28

imagePullPolicy: IfNotPresent

name: busybox

command:

  • “/bin/sh”

  • “-c”

  • “sleep 3600”

pod/second-pod-affinity created

[root@master1 pod_study]# kubectl get pods -o wide

5. 污点与容忍度（Taints[[teɪnt]]{.mark} & Tolerations[[ˌtɒləˈreɪʃn]]{.mark}）

5.1 污点（Taints）

1）核心概念

+————————————————————————————————————-+
| · 污点 Taint（节点属性）: 作用于节点node，给节点贴“拒绝条件”。不被容忍的 Pod 不会调度上来（或被驱逐）。 |
| |
| [· 容忍度 Toleration（Pod 属性）: 声明 Pod 能“接受哪些污点”]{.mark} |
| |
| [⭐ 两者配合使用：]{.mark} |
| |
| [节点”挑 Pod” =]{.mark} 节点说：”我只接受有特定通行证的 Pod” |
| |
| Pod”表态是否能接受” = Pod 说：”我有这个通行证，我能进” |
+————————————————————————————————————-+

2）Taint 的结构与效果

+—————————————————————————————————+
| 结构：key=value:effect |
| |
| 三种 effect（排斥等级）： |
| |
| NoSchedule: 仅影响调度，不影响已在运行的 Pod |
| |
| NoExecute: 影响调度+影响已经运行的 Pod，不能容忍的会被驱逐，有必要是可以设置容忍时间（最高） |
| |
| PreferNoSchedule: 尽量不调度到该节点（软性） |
+—————————————————————————————————+

3）常用命令

+——————————————————————————————————————–+
| # 查看节点污点 |
| |
| kubectl describe node <node-name> | grep Taints |
| |
| [root@master1 ~]# kubectl describe node master| grep Taints |
| |
| Taints: node-role.kubernetes.io/control-plane:NoSchedule |
| |
| # 添加污点 |
| |
| kubectl taint nodes <node-name> <key>=<value>:<effect> |
| |
| [root@master1 ~]# kubectl taint nodes**  node1**  node-type = production:NoSchedule # key=value:effect |
| |
| #删除污点 |
| |
| kubectl taint nodes <node-name> <key>:<effect> |
| |
| [root@master1 ~]# kubectl taint nodes node1 node-type:NoExecute-    # 删除对应污点 |
| |
| #删除所有污点 |
| |
| kubectl taint nodes <node-name> <key>- |
| |
| kubectl taint nodes node1 node-type-              # 删除所有 node-type 污点 |
+——————————————————————————————————————–+

3）当节点都有污点无法调度时，Pod的创建就需要有容忍度才能被调度

1）完全匹配[（Equal）]{.mark}

tolerations:

- key: “node-type”

operator: “Equal” # 完全匹配

value: “production”

effect: “NoSchedule” # 注意：effect 也要完全一致

例子

[root@master1 pod_study]# cat pod-demo-1-wrong.yaml

apiVersion: v1

kind: Pod

metadata:

name: tolerations-test

namespace: default

labels:

app: myapp

release: v1

spec:

containers:

  • name: myapp

image: ikubernetes/myapp:v1

imagePullPolicy: IfNotPresent

ports:

  • containerPort: 80

tolerations:

  • key: “node-type”

operator: “Equal” # 等于，也就是完全匹配

value: “sweet”

effect: “NoExecute” # key=value的值是node-type=sweet:NoSchedule(刚刚对node1的污点定义)，所以这个地方完全匹配NoExecute就是错误的

tolerationSeconds: 3600 #⭐⭐ 这一项是NoExecute排斥等级最高的effect专属，其它设置会报错

⭐ Pod 会一直 Pending，因为：

node1 的污点是 node-type=sweet:NoSchedule

Pod 的容忍度是 node-type=sweet:NoExecute

effect 不匹配！

修改后看看是否能正常运行

2）存在匹配[（Exists）]{.mark}

tolerations:

- key: “node-type”

  operator: “Exists”     # 只要这个key和effect存在且匹配上对应的污点就行，值value忽略。

  effect: “NoSchedule”

⭐注：存在key和effect与污点对应即可，设置Exists时，value必须为空

  • name: myapp

imagePullPolicy: IfNotPresent

ports:

  • containerPort: 80

  • key: “node-type”

operator: “Exists” # Exists 时 value 必须为空，key和effect匹配即可

value: “”

effect: “NoExecute” # 测试它是否能调度掉node2 (node2 node-type=dev:NoExecute) 与此时容忍度的设置是匹配的

# 最初我们在节点上打的两个污点分别是：

node1 node-type=sweet:NoSchedule

node2 node-type=dev:NoExecute

3）最宽松：容忍所有（Exists + effect 省略）

tolerations:

- key: “node-type”

operator: “Exists” # 有这个键就容忍

effect: “” # 值value、效果effect都不限制（相当宽松）

例子

apiVersion: v1

kind: Pod

metadata:

name: tolerations-test

namespace: default

labels:

app: myapp

release: v1

spec:

containers:

  • name: myapp

image: ikubernetes/myapp:v1

imagePullPolicy: IfNotPresent

ports:

  • containerPort: 80

tolerations:

  • key: “node-type”

operator: “Exists”  

value: “” # Exists 时 value 必须为空

effect: “” # 最宽松：不限制 effect

⭐结果：

Pod 可以调度到node1或node2

1、只要节点有 node-type 这个 key 的污点，Pod 都能容忍

2、不管 value 是 sweet 还是 dev

3、不管 effect 是 NoSchedule 还是 NoExecute

5.3 实际应用场景

+———————————————————————–+
| 生产环境隔离：给生产节点打污点，只有生产Pod能调度 （dev） |
| |
| → pod就用exists，value置空，key和effect匹配即可（存在匹配） |
| |
| 特殊硬件：GPU节点打污点，只有需要GPU的Pod能调度 （存在匹配） |
| |
| 维护模式：给节点打NoExecute污点，驱逐所有Pod（完全匹配） |
+———————————————————————–+

6. Pod状态与重启策略

6.1 ⭐常见Pod状态

第一阶段状态 (初始阶段 / 调度前/刚创建）

Pending：等待调度，找不到合适节点

Failed：容器异常退出（非0状态码）

Unknown：无法获取状态**（通常kubelet故障）**

Succeeded：所有容器正常终止

第二阶段状态 (运行期 / 初始化后 / 运行中)

Unschedulable：无法调度

PodScheduled：正在调度中

Initialized：初始化容器完成

ImagePullBackOff：镜像拉取失败

Running：容器正常运行

其他状态

Evicted：资源不足被驱逐

CrashLoopBackOff：容器反复崩溃重启
