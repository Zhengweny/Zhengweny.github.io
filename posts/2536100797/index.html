一、Deployment控制器：概念、原理解读

官网：https://kubernetes.io/docs/concepts/workloads/controllers/deployment/

+————————————————————————————————————————————————————————————————————————————————————————————————————————————–+
| 1、Deployment概述 |
| |
| 1.1 核心定位 |
| |
| Deployment是K8s核心工作负载控制器，基于声明式定义管理ReplicaSet和Pod：描述期望状态后自动收敛。核心依赖：Deployment→ReplicaSet→Pod，删除Deployment会级联删除关联资源。 |
| |
| 1.2 核心优势（对比ReplicaSet） |
| |
| 对比ReplicaSet（仅维持副本数），Deployment核心优势：支持滚动升级、回滚等发布策略；支持声明式更新（kubectl apply直接生效）。 |
| |
| 1.3 核心机制 |
| |
| Deployment管理多版本RS（仅1个活跃），核心流程： |
| |
| 初始创建：Deployment生成RS(v1)，RS(v1)创建目标Pod； |
| |
| 版本更新：更新镜像后apply，生成RS(v2)，按策略迁移Pod至新RS； |
| |
| 版本回滚：保留旧RS，可快速回滚至历史版本。 |
| |
| 2、 Deployment工作原理 |
| |
| 2.1 核心管控逻辑 |
| |
| 基于声明式API收敛状态，支持两种更新方式： |
| |
| 1、补丁式修改：命令行直接打补丁（如kubectl set image）修改资源版本； |
| |
| 2、策略控制：通过配置更新策略，自定义更新节奏（新增/删除Pod的速率）和逻辑（可用Pod数量阈值）。 |
| |
| 2.2 更新节奏与逻辑详解 |
| |
| 核心由maxSurge（最多超量副本）和maxUnavailable（最多不可用副本）控制，需配合就绪探针确保新Pod就绪后删旧Pod |
| |
| 2.3 核心能力清单 |
| |
| 1) 创建ReplicaSet和Pod； |
| |
| 2) 滚动升级与版本回滚； |
| |
| 3) 平滑扩容/缩容； |
| |
| 4) 更新暂停与恢复。 |
| |
| 三、Deployment资源清单编写要点 |
| |
| 3.1 核心结构（4大必选字段） |
| |
| apiVersion: apps/v1 # 固定版本 kind: Deployment # 资源类型 metadata: # 元数据（名称、命名空间等） name: xxx spec: # 核心配置（必选） replicas: 3 # 副本数 selector: {} # 标签选择器（关联Pod） strategy: {} # 更新策略 template: {} # Pod模板（必选） status: {} # 状态字段（只读） |
| |
| 3.2 关键配置详解 |
| |
| 3.2.1 基础控制字段 |
| |
| minReadySeconds：新Pod创建后等待多久再开始升级（如6秒，确保应用启动完成）； |
| |
| paused：是否暂停更新（布尔值true/false，更新时可先暂停排查）； |
| |
| progressDeadlineSeconds：升级卡住的超时时间（超时后标记状态为False，需手动处理）； |
| |
| revisionHistoryLimit：保留的历史RS版本数（默认10，用于回滚）。 |
| |
| 3.2.2 更新策略（strategy） |
| |
| 支持两种类型，默认RollingUpdate： |
| |
| Recreate（重建式更新）：先删除所有旧Pod，再创建新Pod（会中断服务，适用于不可多版本共存场景）； |
| |
| RollingUpdate（滚动更新）：通过两个核心参数控制更新过程（⭐⭐⭐面试高频考点）： |
| |
| maxSurge：更新时最多允许超出目标副本数的数量/比例（默认25%），计算时小数向上取整（如5副本×25%=1.25→取2，最多7个Pod）； |
| |
| maxUnavailable：更新时最多允许不可用的副本数/比例（默认25%），计算时小数向下取整（如5副本×25%=1.25→取1，最少4个可用）。 |
| |
| 3.2.3 Pod模板（template） |
| |
| Pod模板与独立Pod的核心区别： |
| |
| 无需指定apiVersion和kind字段； |
| |
| 必须包含metadata（用于添加标签，与上面的选择器selector关联）； |
| |
| template.spec字段与Pod的spec完全一致（定义容器、探针等）。 |
| |
| ⭐⭐⭐核心面试考点 |
| |
| 1、面试题面试题： |
| |
| replicas=5，maxSurge=25%，maxUnavailable=25%，求最多/最少Pod数？ |
| |
| 解答：maxSurge=5×25%≈2→最多7个；maxUnavailable=5×25%≈1→最少4个。 |
| |
| 2、核心关系： |
| |
| Deployment管理多版本RS，更新生成新RS（仅1个活跃）；旧RS保留用于回滚，数量由revisionHistoryLimit控制（spec下参数，默认保留10个版本） |
+————————————————————————————————————————————————————————————————————————————————————————————————————————————–+

二、Deployment使用案例：创建一个web站点

1、⭐Deployment概述

+—————————————————————————————————+
| Deployment是一个三级结构： |
| |
| Deployment 管理 ReplicaSet |
| |
| ReplicaSet 管理 Pod |
| |
| Deployment提供了Pod的声明式更新、滚动更新、回滚等功能，是是 Kubernetes 中最常用的资源控制器之一。 |

四、通过 K8s 实现滚动更新

1、滚动更新简介

+——————————————————————————————+
| ·1）基本逻辑： |
| |
| 逐步用新版本 Pod 替换旧版本，分批次进行 |
| |
| 每批更新后留观察窗口，确认无异常再继续 |
| |
| 优势：用户体验平滑，避免服务中断；缺点：整体更新速度较慢（但是很稳，生产环境也几乎都用滚 |
| |
| 动更新RollingUpdate，不可能随意去用另一种更快的Recreate 重建策略） |
| |
| 2）[批次控制：]{.mark} |
| |
| 每次更新的数量 / 比例由两个参数决定（可自定义） |
| |
| maxSurge：允许超出目标副本数的最大比例（默认 25%），控制每次新增多少新版本 Pod |
| |
| maxUnavailable：允许不可用的最大比例（默认 25%），控制每次销毁多少旧版本 Pod |
| |
| ⭐计算方式： |
| |
| 比如replicas=10（10个副本，也就10个pod） |
| |
| maxSurge=25%，10*0.25=2.5个 → 向上取整，即3，每次最多同时新增3个新版本 |
| |
| maxUnavailable=25%，10*0.25=2.5个 → 向下取整，即2，每次同时销毁最多2个旧版本（不可用） |
+——————————————————————————————+

2、Deployment 核心字段速览（kubectl explain）

+———————————————————————————————–+
| spec.minReadySeconds：[新创建的 Pod 必须持续处于 Ready 状态的最短时间（秒数）]{.mark}，默认 0 |
| |
| spec.paused：暂停 Deployment（配合金丝雀发布） |
| |
| spec.progressDeadlineSeconds：进度超时阈值，默认 600s |
| |
| spec.replicas：期望副本数，默认 1 |
| |
| spec.revisionHistoryLimit：保留历史 RS 数([ReplicaSet管理pod的]{.mark})，默认 10 |
| |
| spec.selector：Pod 选择器（必须与模板 labels 匹配） |
| |
| spec.strategy.type：Recreate（重建） 或 RollingUpdate（默认滚动更新 RollingUpdate） |
| |
| spec.strategy.rollingUpdate.maxSurge：允许超出期望副本的最大数量/比例（向上取整） |
| |
| spec.strategy.rollingUpdate.maxUnavailable：更新时允许的最大不可用数量/比例（向下取整） |
| |
| 结构层级：Deployment → ReplicaSet → Pod |
+———————————————————————————————–+

滚动更新的“先上后下”：

4、自定义滚动更新策略

+———————————————————————————————————-+
| 1. 参数作用 |
| |
| maxUnavailable：更新中允许的最大不可用 Pod 数（或比例），值越小越稳定。 |
| |
| maxSurge：更新中允许超出期望副本数的最大临时 Pod 数（或比例），值越大更新越快。 |
| |
| 2. 取值规则 |
| |
| 数值：均需在 [[0, 副本数]]{.mark} 范围内，且maxUnavailable和maxSurge不能同时为 0（否则更新停滞）。 |
| |
| ⭐比例：均需在 [[0%, 100%]]{.mark} 范围内： |
| |
| maxUnavailable 向下取整（如 10 副本的 5% →0）；也就是默认滚动更新中，都要保持10个可用 |
| |
| maxSurge 向上取整（如 10 副本的 5% → 1），默认滚动更新中，最多临时保持11个可用 |
| |
| 3. 推荐配置与效果 |
| |
| 生产默认：maxUnavailable=0 + maxSurge=1 |
| |
| 逻辑：“一上一下，先上后下”（新 Pod 就绪后再删旧 Pod）。 |
| |
| 特点：最平滑，服务无中断，但更新较慢。 |
| |
| 自定义示例：maxUnavailable=1 + maxSurge=1（3 副本场景，在[0,3]中取） |
| |
| 逻辑：最少 2 个可用 Pod（3-1=2），最多临时 4 个 Pod（3+1=4）.a |
| |
| 特点：更新更快，兼顾稳定性。 |
+———————————————————————————————————-+

[root@master1 deployment_study]# cat deploy-demo.yaml

apiVersion: apps/v1

kind: Deployment

metadata:

name: myapp-v1

spec:

strategy: # 增加策略及策略规则

rollingUpdate:

maxSurge: 1 # 副本为3，滚动更新时，允许临时最多可用有4个pod (3+1=4)

maxUnavailable: 1 # 3-1=2，滚动更新时，至少要保证2个是可用的（允许不可用是1个嘛，3-1=2，至少要2个可用）

replicas: 3 # 副本数为3

selector:

matchLabels:

app: myapp

version: v1

template:

metadata:

labels:

app: myapp

version: v1

spec:

containers:

  • name: myapp

image: janakiramm/myapp:v2 # 重新触发下镜像，才会进行滚动更新

imagePullPolicy: IfNotPresent

ports:

  • containerPort: 80

# 重新更新下发

[root@master1 deployment_study]# kubectl apply -f deploy-demo.yaml

# 观察如下图

[root@master1 ~]# kubectl get pods -l app=myapp -w

5、[重建式策略Recreate]{.mark}

注意：更新会全部旧Pod都下掉，再全部新pod都创建，这种对生产业务影响非常大（几乎不用）

[root@master1 deployment_study]# cat deploy-demo.yaml

apiVersion: apps/v1

kind: Deployment

metadata:

name: myapp-v1

spec:

strategy: # 更新策略类型

type: Recreate # 换成重建式recreate

replicas: 3

selector:

matchLabels:

app: myapp

version: v1

template:

metadata:

labels:

app: myapp

version: v1

spec:

containers:

  • name: myapp

image: janakiramm/myapp:v1 # 要改动下镜像才叫做更新

imagePullPolicy: IfNotPresent

ports:

  • containerPort: 80

# 重新更新下发

[root@master1 deployment_study]# kubectl apply -f deploy-demo.yaml

# 观察如下图

[root@master1 ~]# kubectl get pods -l app=myapp -w

五、生产环境如何实现蓝绿部署

1、什么是蓝绿部署

+—————————————————————————————-+
| 蓝绿部署通过两套独立系统实现版本切换： |
| |
| 绿色系统：正在对外提供服务的旧版本系统。 |
| |
| 蓝色系统：新部署的新版本系统，初期不对外服务，仅用于测试验证。 |
| |
| 流程： |
| |
| 部署蓝色系统（新版本）并完成测试验证； |
| |
| 切换流量至蓝色系统（此时蓝色系统对外服务，绿色系统备用）； |
| |
| 观察无问题后，蓝色系统成为新的绿色系统，旧绿色系统销毁释放资源，用于部署下一个蓝色系统 |
| |
| 若出现问题，立即切回绿色系统，实现快速回滚。 |
+—————————————————————————————-+

2、蓝绿部署的优势和缺点

+———————————————————————–+
| 优点： |
| |
| 无停机更新，风险低； |
| |
| 回滚便捷（仅需切换路由 / DNS）。 |
| |
| 缺点： |
| |
| 成本高（需两套环境）； |
| |
| 新版本问题可能瞬间影响全量用户； |
| |
| 环境隔离不足时存在被破坏风险； |
| |
| 路由 / DNS 配置不当可能导致流量切换失败。 |
+———————————————————————–+

六、通过 K8s 完成线上业务的金丝雀发布

1、金丝雀发布简介

+——————————————————————————————————+
| 金丝雀发布（灰度发布）：小比例部署新版本（如 1 个 Pod 或 2% 流量）验证，通过则全量升级，失败则回退。 |
| |
| 优点：策略灵活，问题影响范围小。 |
| |
| 缺点：未覆盖全量用户，部分问题难排查。 |
+——————————————————————————————————+

2、K8s 实现金丝雀发布（基于 Deployment 的暂停 / 恢复机制）

[核心逻辑：更新 Deployment 镜像后立即暂停滚动更新，仅启动少量 “金丝雀 Pod” 验证，无问题再恢复更新全量 Pod。]{.mark}
