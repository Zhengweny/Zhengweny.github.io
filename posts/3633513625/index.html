一、概念与原理解读

1.1 核心作用（为什么需要 Service？）

+————————————————————————————————————+
| Pod IP 具有动态性（重启 / 重建后会变化），直接写死 Pod IP 会导致服务不可用； |
| |
| Pod IP 仅集群内可见，外部无法访问； |
| |
| Service 解决：提供固定访问入口，关联一组 Pod（通过标签选择器），实现请求代理转发，同时支持集群外访问。 |
+————————————————————————————————————+

1.2 Service 概述

+———————————————————————————————————————————————–+
| 本质：固定接入层，客户端通过 Service 的 IP + 端口访问后端 Pod 集群； |
| |
| 依赖组件： |
| |
| DNS 插件（1.11 前 kubeDNS，新版本 CoreDNS）：实现 Service 名称解析； |
| |
| 网络插件（flannel/calico 等）：提供 K8S 集群网络功能； |
| |
| ⭐⭐kube-proxy（每个节点都有）：都盯着集群 “大脑”（APIServer），一旦应用入口（Service）或实例（Pod）变动，就更新本机转发规则（iptables/ipvs） |
+———————————————————————————————————————————————–+

1.3 工作原理

+————————————————————————————————————————————————————————————+
| Service 通过selector label匹配目标 Pod； |
| |
| 自动创建同名Endpoint对象（endpoint和service同名），记录匹配 Pod 的「IP + 端口」；Endpoint属于Pod和Service的桥梁； |
| |
| Pod 变动时（删除 / 重建），Endpoint 同步更新； |
| |
| 客户端请求 Service → kube-proxy 通过转发规则 → Endpoint 查找可用 Pod→转发请求。 |
| |
| （⭐⭐**注：**kube-proxy 只知道 “要把 Service 的请求转发给 Pod”，但它不知道具体是哪些 Pod，所以kube-proxy就会去etcd库里找到Endpoint记录的 IP+端口清单，此时就知道转发给哪个Pod了） |
+————————————————————————————————————————————————————————————+

1.4 K8S 三类 IP 地址

[类型]{.mark} [说明]{.mark} [示例]{.mark}

[Node Network**（节点node IP）**]{.mark} 物理 / 虚拟节点的真实 IP，配置在节点网卡上 192.168.1.63（ens33 接口）

Pod Network**（Pod IP）** Pod 的真实 IP，配置在 Pod 资源上，集群内互通 10.244.187.76

Cluster Network**（Service IP）** 虚拟 IP（VIP），未配置在任何接口，仅存在于转发规则中 10.96.0.1（默认 kubernetes 服务）

二、Service 资源定义规范

2.1 核心字段（kubectl explain service）

字段 说明

[apiVersion]{.mark} [接口版本（固定 v1）]{.mark}

[kind]{.mark} [资源类型（固定 Service）]{.mark}

[metadata]{.mark} [元数据（名称、标签等）]{.mark}

[spec]{.mark} [核心配置（类型、端口、标签选择器等）]{.mark}

[spec.selector]{.mark} [标签选择器，关联目标 Pod（必填）]{.mark}

[spec.type]{.mark} [Service 类型（默认 ClusterIP）]{.mark}

[spec.ports]{.mark} [端口映射配置（必填）]{.mark}

2.2 Service 四种类型（spec.type）

+———————————————————————————–+
| ClusterIP：默认类型，仅集群内访问（虚拟 IP）； |
| |
| NodePort：基于 ClusterIP，在所有节点开放固定端口（30000-32767），支持集群外访问； |
| |
| LoadBalancer：基于 NodePort，集成云厂商负载均衡器（云环境可用）； |
| |
| ExternalName：将 Service 映射到外部域名（无 selector，不关联 Pod）。 |
+———————————————————————————–+

2.3 端口配置（spec.ports）

字段 说明

name 端口名称（可选）

port Service 暴露的端口（集群内访问用，必填）

targetPort Pod 容器的端口（流量最终转发目标）

nodePort NodePort 类型时，节点开放的端口

protocol 协议（默认 TCP）

2.4 会话亲和性（sessionAffinity）

+———————————————————————–+
| 默认None：随机调度（基于 iptables/ipvs）； |
| |
| ClientIP：同一客户端 IP 的请求转发到同一个 Pod。 |
+———————————————————————–+

4）关键说明

+—————————————————————————————-+
| ClusterIP 仅集群内访问，外部（如浏览器）无法直接访问，需改用 NodePort 类型； |
| |
| Service 不直接关联 Pod，而是通过 Endpoint 维护 Pod 地址列表； |
| |
| kube-proxy 通过 ipvs/iptables 实现负载均衡（默认随机调度，支持 ClientIP 会话亲和性）； |
| |
| 可通过ipvsadm -L查看转发规则关联关系。 |
+—————————————————————————————-+

四、NodePort 类型 Service

4.1 作用与特点

+———————————————————————–+
| 基于 ClusterIP，在所有节点开放固定端口（默认 30000-32767）； |
| |
| 支持集群外访问（通过节点 IP+NodePort）； |
| |
| 保留 ClusterIP 特性（集群内可通过 Service IP 访问）。 |
+———————————————————————–+

五、ExternalName 类型 Service

5.1 核心理解

+——————————————————————————————————————————————————————–+
| [是什么？ExternalName 是 Service 的 “特殊类型”，不关联任何 Pod，本质是 “域名别名”；]{.mark} |
| |
| 做什么？：[将当前命名空间的 Service 作为访问入口，指向目标外部域名（含其他命名空间的 Service 域名），支持通过本地 Service 名称访问跨域或外部资源。]{.mark} |
| |
| [#⭐举例：]{.mark} |
| |
| [目标地址：「命名空间 B」下的 mysql-service 域名【mysql-service.b.svc.cluster.local】]{.mark} |
| |
| [你可以在「命名空间 A」下起一个的db域名 （相当于一个别名）【db.a.svc.cluster.local】（ExternalName类型Service）]{.mark} |
| |
| 那么，[当「命名空间 A」下的 pod)访问db.a.svc.cluster.local时，k8s会自动将请求转发到mysql-service.b.svc.cluster.local。]{.mark} |
| |
| [db.a.svc.cluster.local（命名空间 A 的 ExternalName Service）是访问入口 / 别名；]{.mark} |
| |
| [mysql-service.b.svc.cluster.local（命名空间 B 的 Service）是真实目标地址。]{.mark} |
+——————————————————————————————————————————————————————–+

# 以上测试二者是等价的

⭐六、k8s最佳实践：映射外部服务案例分享

6.1 核心目的

让K8s集群内部的Pod能像访问集群内服务一样，访问集群外的外部服务（如外部MySQL）

6.2 案例

1）前置准备：在外部节点安装MySQL

在node节点上（非master节点）上安装并启动MySQL（这里用mariadb替代，兼容MySQL）：

# 安装mariadb服务

[root@xianchaonode2 ~]# yum install mariadb-server.x86_64 -y

# 启动服务

[root@xianchaonode2 ~]# systemctl start mariadb

2）关键原理：Service+Endpoints组合

Service 缺标签（即没有关联selector）选不到外部服务，用 Endpoints 搭桥（关联外部 IP），让 Service 能代理外部服务。

3） 实操步骤

步骤1：创建无selector的Service（仅做代理）

创建一个不关联标签选择器selector的Service，此时它不会自动关联任何Pod，Endpoints为空。

# mysql_service.yaml

apiVersion: v1

kind: Service

metadata:

name: mysql # Service名称，后续Endpoints要和它同名

spec:

type: ClusterIP # 集群内部可访问的类型

ports:

  • port: 3306 # Service暴露的端口，对应MySQL默认端口

[root@xianchaomaster1]# kubectl apply -f mysql_service.yaml service/mysql created

# 查看Service，此时Endpoints为空

[root@master1 service_study]# kubectl get svc | grep mysql

mysql ClusterIP 10.110.228.158 <none> 3306/TCP 17s

[root@xianchaomaster1]# kubectl describe svc mysql

Name: mysql

Namespace: default

Selector: <none> # 无选择器，不关联PodType:

ClusterIP

IP: 10.110.228.158

Port: <unset> 3306/TCP

TargetPort: 3306/TCP

Endpoints: <none> # 未关联外部IP时为空

Events: <none>

步骤2：创建Endpoints关联外部MySQL IP

Endpoints的作用：“告诉Service外部服务的真实IP”

**Endpoints名称必须和Service完全一致，**才能绑定成功。

# mysql_endpoint.yaml （kubectl explain ep 简写为ep即可查看字段）

apiVersion: v1

kind: Endpoints

metadata:

name: mysql # 必须和Service名称一致

subsets:

- addresses:

  • ip: 192.168.40.182 # 外部MySQL所在节点（node2）的IP

ports:

  • port: 3306 # 外部MySQL的端口

# 应用配置

[root@xianchaomaster1]# kubectl apply -f mysql_endpoint.yaml

endpoints/mysql created

# 再次描述Service，确认Endpoints已关联外部IP

[root@xianchaomaster1]# kubectl describe svc mysql

…

Endpoints: 192.168.40.182:3306 # 已关联外部MySQL的IP:端口

…

步骤3：效果验证

此时K8s集群内的Pod只需访问“mysql:3306”（Service名称+端口），就会通过Service代理访问到外部的192.168.40.182:3306的MySQL服务。

（k8s内Pod访问：mysql:3306 就相当于 外部访问 192.168.40.182:3306 【服务器IP:3306】）

七、K8s服务发现：CoreDNS组件

7.1 基础概念

+—————————————————————————————+
| DNS：域名系统，用【好记的域名】对应 【复杂的IP】 |
| |
| CoreDNS：K8s集群内置的DNS服务，专门负责把K8s的Service名称翻译成Service的ClusterIP |
+—————————————————————————————+

7.2 验证CoreDNS是否正常工作

通过部署一个带“dig/nslookup”工具的Pod，测试域名解析功能。

步骤1：导入工具镜像并部署测试Pod

# 1. 上传dig.tar.gz到节点，导入镜像（两个节点都执行）

[root@chaonode2 ~]# ctr -n=k8s.io images import dig.tar.gz

[root@chaonode1 ~]# ctr -n=k8s.io images import dig.tar.gz

# 2. 创建测试Pod的配置文件dig.yaml

[root@xianchaomaster1 ~]# cat dig.yaml

apiVersion: v1

kind: Pod

metadata:

name: dig

namespace: default

spec:

containers:

  • name: dig

image: xianchao/dig:latest

imagePullPolicy: IfNotPresent

command:

  • sleep

  • “3600” # 让Pod持续运行1小时，方便测试

restartPolicy: Always

# 3. 部署Pod

[root@xianchaomaster1 ~]# kubectl apply -f dig.yaml

pod/dig configured

步骤2：测试域名解析（核心验证）

进入测试Pod，用nslookup解析K8s默认的“kubernetes”服务，能解析出IP说明CoreDNS正常。

# 进入digPod的命令行

[root@xianchaomaster1 ~]# kubectl exec -it dig – /bin/sh

# 解析k8s默认服务“kubernetes”

# nslookup kubernetes

Server:10.96.0.10 # CoreDNS的IP（即kube-dns的IP）

Address:10.96.0.10#53

Name:kubernetes.default.svc.cluster.local # 服务的完整域名（FQDN）

Address: 10.96.0.1 # kubernetes服务的ClusterIP，解析成功！

步骤3：找到CoreDNS的真实身份

# 1. 查看kube-system命名空间的Service，10.96.0.10是kube-dns的IP

[root@master1 ~]# kubectl get svc -n kube-system kube-dns

7.3 核心总结

+———————————————————————————————————–+
| 1、外部服务映射：无selector的Service + 手动设置Endpoints（Endpoints填外部IP，Service和Endpoints同名即可） |
| |
| 2、CoreDNS作用：把Service名称翻译成ClusterIP |
| |
| 3、Service域名规则：service服务名.命名空间.svc.cluster.local，集群内直接用这个域名访问。 |
| |
| 4、CoreDNS验证：部署dig Pod，nslookup kubernetes能出IP就代表正常。 |
