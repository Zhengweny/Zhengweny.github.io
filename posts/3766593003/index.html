一、核心概述：认证、授权、准入控制的作用

k8s靠APIserver对外提供服务，为了防止非法访问和误操作，设计了三道“安全关卡”，顺序是：认证 → 授权 → 准入控制，层层递进保障集群安全。

1.1 认证：确认“你是谁”（合法用户身份校验）

**核心目的：**验证访问APIserver的用户是否合法，避免陌生人随意访问。

1.2 授权：确认“你能做什么”（合法用户权限校验）

**核心目的：**认证通过仅代表你是可信用户，但不代表你能做所有操作，授权就是明确你拥有的操作权限（比如你只能看资源，还是能删除资源，还是说都可以）。

关键说明：最常用的授权方式是RBAC（基于角色的访问控制）。

1.3 准入控制：最后一道“过滤门”（资源操作的变更与验证）

**核心目的：**用户通过认证和授权后，在资源被持久化到etcd（k8s数据存储中心）前，做最后的验证/修改，类似“插件”可扩展。

典型场景：创建Pod时，我们定义的资源上下限（CPU/内存），如果不符合集群LimitRange规则（这里其实就是准入控制器，有自己的一套标准），准入控制器LimitRanger会直接拒绝创建。

**示例注释：**比如给test-aa命名空间设了“最多用10vCPU、10Gi内存”的限制，该命名空间下所有Pod的资源限制都不能超这个数，否则准入控制不通过。

二、认证详解：k8s客户端访问APIserver的3种认证方式

⭐ 前提：访问k8s集群（操作资源）的主体分两种——

1、外部用户（比如我们用kubectl操作）

2、内部Pod（Pod里的程序访问APIserver），对应不同认证方式。

2.1 客户端认证（双向TLS认证）

**适用场景：**外部用户用kubectl访问APIserver时使用。

核心逻辑：kubectl和APIserver互相验证，都通过CA根证书（集群的“根信任证书”）确认对方合法。

2.2 Bearer Token（令牌认证）

适用场景：外部用户访问APIserver时使用。

核心逻辑：APIserver把“密码”用非对称加密（更安全的加密方式）告诉kubectl，后续访问用这个加密“密码”（令牌）验证身份。

2.3 ServiceAccount（服务账户）

适用场景：集群内部Pod与APIserver交互时使用**（外部访问不用这个）。**

核心逻辑：ServiceAccount包含三部分信息——命名空间、令牌（token）、CA证书；通过“目录挂载”的方式把这些信息传给Pod，Pod启动后读取这些信息，就能合法访问APIserver了。

三、关键配置：kubeconfig文件（kubectl访问集群的“配置指南”）

kubeconfig文件就是记录“访问哪个集群、用哪个用户身份访问”的配置文件，kubectl全靠它找对集群、证明自己的身份。

3.1 官方文档地址

https://kubernetes.io/zh-cn/docs/concepts/configuration/organize-cluster-access-kubeconfig/ （小白可收藏，后续查详细配置用）

3.2 核心作用

告诉kubectl：① 要访问的K8S集群地址（APIserver地址）；② 用哪个用户身份访问（对应前面的认证方式）；③ 当前用哪个配置（上下文contexts）。

3.3 默认位置与查看命令

默认位置：/root/.kube/config （kubectl会优先找这个文件）；

查看配置命令：kubectl config view （执行后就能看到下面的配置内容）。

四、⭐授权核心：RBAC（基于角色的访问控制）

认证通过后用户“一无所有”，必须通过授权才能拥有操作权限。K8S 1.6之后，RBAC是最常用的授权方式

4.1 K8S常用的4种授权插件

+—————————————————————————+
| Node（节点认证）：专门给集群节点授权用； |
| |
| ABAC（基于属性的访问控制）：根据用户属性、资源属性授权，配置复杂，少用； |
| |
| RBAC（基于角色的访问控制）：重点！最常用、最灵活，后续全讲这个； |
| |
| Webhook（基于HTTP回调的访问控制）：把授权判断交给外部服务，适合复杂场景。 |
+—————————————————————————+

4.2 RBAC核心逻辑

+——————————————————————————————————————————-+
| **核心公式：**用户（Users）→ 绑定（Binding）→ 角色（Role/ClusterRole）→ 权限（对资源的操作，比如增删改查） |
| |
| 通俗解释： |
| |
| 1、你（用户）是“开发工程师”（绑定角色），“开发工程师”有“查看项目代码、提交代码”的权限（角色关联权限） |
| |
| 2、你就拥有了这些权限。后续要调整权限，只需要修改角色（“开发工程师”）的权限，所有绑定这个角色的用户都会同步变化，不用一个个改 |
+——————————————————————————————————————————-+

4.3 ⭐RBAC的4个核心组件

+———————————————————————————————————+
| Role（角色）：命名空间级权限集，仅管控单个命名空间资源[（比如只能操作test命名空间的Pod）]{.mark} |
| |
| RoleBinding（角色绑定）：命名空间级绑定，关联用户与 Role/ClusterRole，仅当前命名空间生效 |
| |
| ClusterRole（集群角色）：集群级权限集，管控全集群所有命名空间资源[（比如操作所有命名空间的Pod）]{.mark} |
| |
| ClusterRoleBinding（集群角色绑定）：集群级绑定，关联用户与 ClusterRole，全集群生效 |
+———————————————————————————————————+

4.4 3种RBAC授权方案

方案1：用户 → RoleBinding → Role（命名空间内授权）

逻辑：用RoleBinding把用户绑定到Role上；（命名空间级绑定，关联用户与 Role/ClusterRole，仅当前命名空间生效）

权限范围：只能操作RoleBinding所在命名空间的资源；

示例：把user1通过RoleBinding（作用就是限定命名空间的）绑定到test命名空间的Role1上，user1就只能操作test命名空间的资源，其他命名空间无权操作。

方案2：用户 → RoleBinding → ClusterRole（命名空间内授权，复用权限）

逻辑：用RoleBinding把用户绑定到ClusterRole上；

权限范围：只能操作RoleBinding所在命名空间的资源（ClusterRole本身是集群级，但被RoleBinding限制在当前命名空间**【比如说我是“开发工程师”，其实我的权限到哪里都能用，但这里被RoleBinding限制在当前命名空间】**）；

核心优势：复用ClusterRole的权限，减少重复配置；

注意：对比两种授权方式

有6个命名空间，每个命名空间的用户都需要“管理员权限”。

1、如果用方案1，要创建6个Role（每个命名空间1个）+6个RoleBinding，再分别进行绑定，很麻烦；

2、用方案2，只需要创建1个ClusterRole（定义管理员权限），然后每个命名空间创建1个RoleBinding，把对应用户绑定到这个ClusterRole上，就能实现“每个用户拥有自己命名空间的管理员权限”，大大简化配置。

方案3：用户 → ClusterRoleBinding → ClusterRole（集群级授权）

逻辑：用ClusterRoleBinding把用户绑定到ClusterRole上；

权限范围：可以操作集群内所有命名空间的资源；

4.5 ⭐⭐⭐关键总结

+——————————————————————————+
| Role和RoleBinding是“命名空间级”，ClusterRole和ClusterRoleBinding是“集群级”； |
| |
| RoleBinding绑定ClusterRole，权限仍限制在当前命名空间； |
| |
| ClusterRoleBinding绑定ClusterRole，权限覆盖所有命名空间； |
| |
| RBAC的核心是“角色复用”，通过绑定关系灵活控制权限，是K8S授权的首选方式。 |
+——————————————————————————+

[五、准入控制]{.mark}

5.1 常用准入控制器及启用规则

核心说明：k8s有多个准入控制器模块，关键区分“默认启用”和“需手动启用”，避免配置错误导致集群故障。

默认启用的3个（无需额外配置，定义规则即可生效）：LimitRanger（资源上下限校验）、ResourceQuota（命名空间资源总量限制）、ServiceAccount（服务账户相关校验）；

需注意的废弃控制器：PodSecurityPolicy（PSP，k8s1.25版本废弃）【一般不用，不是重点】: ① 系统默认不启用；② 若要启用，必须先配置好规则并绑定权限，再启用控制器；③ 未配规则先启用会拒绝所有操作，可能导致系统级Pod无法运行，慎用！

5.2 查看APIserver已启用的准入控制器

六、UserAccount与ServiceAccount：两种k8s账户的区别

⭐核心结论：k8s的账户分两类，对应“外部用户”（UserAccount）和“内部Pod”（ServiceAccount），用途完全不同，别混淆！

6.1 UserAccount（用户账户）

适用对象：给集群外部用户使用（比如我们用kubectl操作集群的人）。

关键特点：

1. 默认用户：kubeadm安装的k8s，默认UserAccount是kubernetes-admin（集群管理员）；

2. 认证方式：通过~/.kube/config配置文件中的密钥信息认证（kubectl会自动读取该文件，无需手动输入密钥）。

6.2 ServiceAccount（服务账户）

适用对象：给集群内部Pod使用（Pod里的程序访问APIserver时用）。

关键特点：

1. 命名空间隔离：仅局限于所在的命名空间，不能跨命名空间使用；

2. 默认账号：每个命名空间创建时，会自动生成一个default ServiceAccount；未指定Service Account的Pod，默认使用这个default账号。

七、ServiceAccount（SA）实操案例：创建、绑定Pod及授权

⭐步骤：创建SA账号 → 创建Pod并指定SA → 给SA授权 → 验证权限。

7.1 步骤1：创建ServiceAccount（命名为sa-test）

root@master1 .kube]# kubectl create sa sa-test

# sa是ServiceAccount的缩写，这条命令会在当前命名空间（默认是default）创建一个叫sa-test的服务账户。

  • name: sa-tomcat

八、RBAC认证授权策略

8.1 RBAC核心介绍

+——————————————————————————————————————————————————————–+
| K8s所有资源操作均通过API完成，资源存储于etcd，访问需经kube-apiserver。Service Account是APIServer的认证过程，授权机制则通过**RBAC（基于角色的访问控制）**实现。 |
| |
| 核心逻辑：通过“角色”聚合权限，再绑定到用户/服务账户，实现精细化管控。 |
| |
| RBAC四大核心资源：Role（角色）、ClusterRole（集群角色）、RoleBinding（角色绑定）、ClusterRoleBinding（集群角色绑定）。 |
+——————————————————————————————————————————————————————–+

8.2 Role：命名空间级权限集合

核心定义：一组权限的集合，仅作用于单个命名空间，仅能授权该命名空间内资源；

集群级资源（如Node）需用ClusterRole。

示例：定义“读取rbac命名空间下Pod”的Role（yaml）：

apiVersion: rbac.authorization.k8s.io/v1

kind: Role

metadata:

namespace: rbac # 所属命名空间（必指定）

name: pod-read # 角色名称

rules: # 权限规则（核心）

- apiGroups: [“”] # Pod默认属v1组（空字符串对应v1）

resources: [“pods”] # 授权资源（Pod）

resourceNames: [] # 具体资源名（空=所有Pod）

verbs: [“get”,”watch”,”list”] # 允许操作：查看、监听、列表查询

⭐rules参数详解：

+——————————————————————————————————————————————————————+
| apiGroups：支持的API组列表（如“apps”对应Deployments等【kubectl explain deploy可用看到GROUP为apps，apps对应的就是deploy的组】，空字符串对应核心组v1 → 例如pod）； |
| |
| resources：授权资源列表（如pods、deployments、secrets等）； |
| |

8.3 ClusterRole：集群级权限集合（无命名空间限制）

核心定义：权限覆盖整个集群，除具备Role的命名空间资源授权能力，还支持集群级资源、非资源路径(类似于http接口）授权。

ClusterRole特殊授权场景：

集群范围资源（如Node、Namespace）；

非资源型路径（如/healthz健康检查接口）；

所有命名空间资源（如全集群Pods、Secrets）

示例：定义“访问所有命名空间Secrets”的ClusterRole：

apiVersion: rbac.authorization.k8s.io/v1

kind: ClusterRole

metadata:

name: secrets-clusterrole # 集群角色名（无命名空间）

rules:

- apiGroups: [“”] # Pod默认属v1组（空字符串对应v1）

resources: [“secrets”] # 授权所有Secrets资源，注意这个地方要写上复数，比如deployments、pods、

services等等

verbs: [“get”,”watch”,”list”] # 允许查看、监听、列表查询

8.4 RoleBinding与ClusterRoleBinding：权限绑定

⭐核心作用：将Role/ClusterRole绑定到主体（User、Group、Service Account），实现“主体→角色→权限”关联。

核心区别：RoleBinding仅单命名空间生效；ClusterRoleBinding全集群生效（任意命名空间）。

8.4.1 RoleBinding：命名空间内权限绑定

场景1：Role绑定用户（单命名空间生效）

示例：将rbac命名空间的pod-read（role）角色授予用户es：

[root@master1 role]# cat pod-read-bind.yaml

apiVersion: rbac.authorization.k8s.io/v1

kind: RoleBinding

metadata:

namespace: rbac # 所属命名空间（需与Role一致）

name: pod-read-bind # RoleBinding名称

subjects: # 绑定主体（用户es）

kind: User

name: es # 用户为es

apiGroup: rbac.authorization.k8s.io #⭐当 kind 为 User/Group 时：apiGroup 为 rbac.authorization.k8s.io;当 kind 为 ServiceAccount 时：apiGroup 为 “”

roleRef: # 绑定角色（关联pod-read）

kind: Role

name: pod-read

apiGroup: rbac.authorization.k8s.io #⭐roleRef.apiGroup默认为rbac.authorization.k8s.io

⭐结论：用户es通过kubectl 仅能在rbac命名空间执行pod-read权限（查看Pod）。

场景2：ClusterRole绑定用户（权限限当前命名空间）

示例：将cluster-admin通过RoleBinding绑定给用户es（仅rbac命名空间生效）：

[root@master1 role]# cat pod-read-bind.yaml

apiVersion: rbac.authorization.k8s.io/v1

metadata:

namespace: rbac # 所属命名空间（需与Role一致）

name: es-allresource # RoleBinding名称

subjects: # 绑定主体（用户es）

kind: User

name: es # 用户为es

⭐结论：用户es在rbac命名空间拥有管理员权限，其他命名空间无权限。

8.4.2 ClusterRoleBinding：全集群权限绑定

场景：ClusterRole绑定用户，权限覆盖全集群（如集群管理员授权）

示例：将cluster-admin绑定给用户root，获全集群权限（任意的访问权限ClusterRoleBinding+ClusterRole）

kubectl create clusterrolebinding cluster-binding –clusterrole=cluster-admin –user=root

⭐⭐十三、限制不同用户操作k8s集群（SSL认证+RBAC授权）

核心逻辑（三步走）

生成 SSL 证书：确立用户唯一身份（K8s 通过证书 CN 字段识别用户名）

配置 kubeconfig：将用户凭证、集群信息、上下文关联，实现用户身份切换

绑定 RBAC 角色 / 集群角色：为用户分配具体操作权限（粒度可控）

案例 1：创建用户[lucky]{.mark}，仅允许操作[lucky-test]{.mark}命名空间（命名空间级权限）

[1、建账号①：生成 SSL 身份证书（在 K8s 集群 CA 目录操作）]{.mark}

[「生成私钥（*.key） → 申请证书（*]{.mark}.csr[） → CA 签发有效证书（*.crt）」]{.mark}

.csr[（全称 Certificate Signing Request）: 证书签名请求（申请证书）]{.mark}

.crt[（全称 Certificate）：证书]{.mark}

# 进入证书目录

cd /etc/kubernetes/pki/

# 生成私钥（umask 077确保私钥安全，仅当前用户可读）

# 解释：

# 1、写法(…;…)是shell的写法，用“;”号隔离命令，这里就是两个命令

# 2、umask是 “权限掩码”，文件的默认最大权限是666,目录默认最大权限是777。

# umask 077，就是用默认权限去扣除，这里是文件，6-0=6，6-7=0，6-7=0

# 为啥不写066呢？因为077可以完整的覆盖目录，以防万一（7-7=0）

# 2048密钥长度

执行： (umask 077; openssl genrsa -out lucky.key 2048)

# 生成证书签名请求（CN=lucky 指定用户名，核心身份标识）

openssl req -new -key lucky.key -out lucky.csr -subj “/CN=lucky”

# CA签名生成有效证书（有效期10年，由集群根CA签发）

openssl x509 -req -in lucky.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out lucky.crt -days 3650

# 生成<用户名>私钥

[1、建账号①：生成 SSL 身份证书（在 K8s 集群 CA 目录操作，用户为lucky666）]{.mark}

[「生成私钥（*.key） → 申请证书（*]{.mark}.csr[） → CA 签发有效证书（*.crt）」]{.mark}

.csr[（全称 Certificate Signing Request）: 证书签名请求（申请证书）]{.mark}

.crt[（全称 Certificate）：证书]{.mark}

# 进入证书目录

cd /etc/kubernetes/pki/

# 生成私钥（umask 077确保私钥安全，仅当前用户可读）

# 解释：

# 1、写法(…;…)是shell的写法，用“;”号隔离命令，这里就是两个命令

# 2、umask是 “权限掩码”，文件的默认最大权限是666,目录默认最大权限是777。

# umask 077，就是用默认权限去扣除，这里是文件，6-0=6，6-7=0，6-7=0

# 为啥不写066呢？因为077可以完整的覆盖目录，以防万一（7-7=0）

# 2048密钥长度

执行： (umask 077; openssl genrsa -out lucky666.key 2048)

# 生成证书签名请求（CN=lucky 指定用户名，核心身份标识）

openssl req -new -key lucky666.key -out lucky666.csr -subj “/CN=lucky666”

# CA签名生成有效证书（有效期10年，由集群根CA签发）

openssl x509 -req -in lucky666.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out lucky666.crt -days 3650

1、核心逻辑

生成SSL证书（确立K8s身份）→ 配置kubeconfig（关联身份）→ RBAC授权（配角色+绑作用域）→ 绑定系统用户（操作系统层面关联）

2、标准化操作流程

步骤 1：生成 SSL 证书（确立 K8s 用户身份）

# 1. 进入CA目录（固定路径）

cd /etc/kubernetes/pki/

# 2. 生成私钥（umask 077保证安全）

(umask 077; openssl genrsa -out <用户名>.key 2048)

# 3. 生成CSR（CN=实际用户名，K8s认这个）

openssl req -new -key <用户名>.key -out <用户名>.csr -subj “/CN=<用户名>“

# 4. CA签发证书（有效期10年）

openssl x509 -req -in <用户名>.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out <用户名>.crt -days 3650

步骤 2：配置 kubeconfig（关联身份）

# 1. 先切回管理员context（避坑第一要务！）

kubectl config use-context kubernetes-admin@kubernetes

# 查看当前生效的 Context

kubectl config current-context

# 2. 添加用户凭证（嵌入证书，避免路径问题）

kubectl config set-credentials <用户名> –client-certificate=./<用户名>.crt –client-key=./<用户名>.key –embed-certs=true

# 3. 创建上下文（格式：用户名@集群名）

kubectl config set-context <用户名>@kubernetes –cluster=kubernetes –user=<用户名>

# 4. （可选）测试切换（授权前切回管理员！）

kubectl config use-context <用户名>@kubernetes # 测试后立刻切回管理员

kubectl config use-context kubernetes-admin@kubernetes

步骤 3：RBAC 授权（分配权限，核心避坑）

# 角色role一般我们用clusterrole即可，比较少用

# 场景1：仅授权单个命名空间（RoleBinding）

kubectl create ns <命名空间名>

kubectl create rolebinding <用户名> -n <命名空间名> –clusterrole=<权限模板> –user=<证书CN用户名>

# 场景2：授权全集群（ClusterRoleBinding）

# 先自定义ClusterRole（比如仅查看所有Pod）

kubectl apply -f - <<EOF

apiVersion: rbac.authorization.k8s.io/v1

kind: ClusterRole

metadata:

name: <用户名>-get-pod

rules:

- apiGroups: [“”]

resources: [“pods”] # 定义资源

verbs: [“get”,”list”,”watch”] # 定义动作，什么权限

EOF

# 绑定全集群权限

kubectl create clusterrolebinding <用户名>-get-pods –clusterrole=<用户名>-get-pod –user=<证书CN用户名>

步骤 4：绑定系统用户（操作系统层面用户的关联）

# 1. 创建OS普通用户

useradd <系统用户名>

# 2. 复制管理员config到临时目录（仅复制config文件，不要cache！）

mkdir -p /tmp/kubeconfig

cp -f /root/.kube/config /tmp/kubeconfig/

# 3. 编辑临时config（仅保留目标K8s用户配置）

# 删kubernetes-admin相关内容，仅保留：clusters + 目标用户context + 目标用户的认证信息

vim /tmp/kubeconfig/config

# 4. 复制到OS用户家目录并设权限

mkdir -p /home/<系统用户名>/.kube

cp -f /tmp/kubeconfig/config /home/<系统用户名>/.kube/

chown -R <系统用户名>.<系统用户名> /home/<系统用户名>/.kube/

chmod 600 /home/<系统用户名>/.kube/config

# 5. 验证（切换OS用户）

su - <系统用户名>

kubectl get pods -n <目标命名空间> # 有权限

kubectl get pods -n default # 无权限（验证隔离）

十四、准入控制

14.1 核心目的

认证、授权通过后，资源保存到etcd前的最后校验，确保符合集群全局规则（如资源限制）

14.2 ResourceQuota（命名空间级资源配额）

核心作用

限制**[整个命名空间]{.mark}**的资源使用总和（非单个 Pod / 容器），防止某命名空间占用过多集群资源，默认启用。

1. (基础资源限制（CPU、内存、Pod/Deployment 数量）

# resourcequota-1.yaml

apiVersion: v1

kind: ResourceQuota # 资源类型：命名空间级资源配额

metadata:

name: quota-test # 配额名称

namespace: quota # 作用的命名空间（需先执行kubectl create ns quota创建）

spec:

hard: # 硬性限制（超了就创建失败）

pods: “6” # 该命名空间最多运行6个Pod

requests.cpu: “2” # 所有Pod的CPU请求（下限）总和 ≤ 2核

requests.memory: 2Gi # 所有Pod的内存请求（下限）总和 ≤ 2G

limits.cpu: “4” # 所有Pod的CPU限制（上限）总和 ≤ 4核

limits.memory: 10Gi # 所有Pod的内存限制（上限）总和 ≤ 10G

count/deployments.apps: “6” # 最多6个Deployment

persistentvolumeclaims: “6” # 最多6个PVC

测试验证

创建 replicas=7 的 Deployment（超 Pod 数限制），最终仅能运行 6 个 Pod，验证配额生效。

2. (存储资源)限制

# resourcequota-2.yaml

apiVersion: v1

kind: ResourceQuota

metadata:

name: quota-storage-test

namespace: quota

spec:

hard:

requests.storage: “5Gi” # 所有PVC存储请求总和 ≤ 5G

persistentvolumeclaims: “5” # PVC总数 ≤5个

requests.ephemeral-storage: “1Gi” # 临时存储请求总和 ≤1G

limits.ephemeral-storage: “2Gi” # 临时存储限制总和 ≤2G

14.3 LimitRanger（容器 / Pod 级资源限制）

核心作用

限制**[单个 Pod / 容器]{.mark}**的资源使用（非总和），可定义默认值、最小值、最大值、上限 / 下限比值，默认启用。

配置文件

# limitrange.yaml

apiVersion: v1

kind: Namespace # 先创建limit命名空间

metadata:

name: limit

— # 分隔符：一个文件定义多个资源

apiVersion: v1

kind: LimitRange # 资源类型：容器/Pod级资源范围限制

metadata:

name: cpu-memory

namespace: limit

spec:

limits:

  • default: # 容器未指定资源上限时，默认值

cpu: 1000m # 默认CPU上限：1核

memory: 1000Mi # 默认内存上限：1G

defaultRequest: # 容器未指定资源下限，默认值

cpu: 500m # 默认CPU下限：0.5核

memory: 500Mi # 默认内存下限：500M

min: # 手动指定的下限，不能小于此值

cpu: 500m # CPU下限最小值：0.5核

memory: 500Mi # 内存下限最小值：500M

max: # 手动指定的上限，不能大于此值

cpu: 2000m # CPU上限最大值：2核

memory: 2000Mi # 内存上限最大值：2G

maxLimitRequestRatio: # 上限÷下限的最大比值

cpu: 4 # CPU上限最多是下限的4倍

memory: 4 # 内存同理

type: Container # 限制级别：针对容器（可选Pod）

测试验证

1、未指定资源的 Pod：创建后自动附加默认资源限制（default/defaultRequest）；

2、指定 CPU 请求 100m[0.1核]（小于下限min的500m[0.5核]）：创建失败，验证最小值限制生效。

⭐总结（核心要点）

ResourceQuota：控命名空间级总量，限制 Pod 数、CPU / 内存 / 存储总和，超配则拒绝创建；

LimitRanger：控单个容器 / Pod，定义默认 / 最小 / 最大资源值，违规则拒绝，未指定资源时自动补默认值；

⭐核心区别：前者管 “总量”，后者管 “单个”，结合使用可精细化管控集群资源。
