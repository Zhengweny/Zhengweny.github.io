一、基础组件：节点与集群监控（硬件层面的监控）

1、[node-exporter]{.mark}：节点指标采集

1.1 前置环境

+———————————————————————————-+
| • k8s集群：1个master节点 + 2个node节点 |
| |
| • master节点：IP 192.168.40.180，主机名 master1（控制节点，执行所有kubectl命令） |
| |
| • node节点：IP 192.168.40.181和192.168.40.182，主机名 node1（工作节点，运行pod） |
| |
| **注意：**先确认容器运行时是docker还是containerd（后续导入镜像命令不同） |
+———————————————————————————-+

[root@master1 ~]# kubectl get nodes -owide

…. CONTAINER-RUNTIME…. containerd://1.6.22     # 用容器运行时

1.2 [node-exporter是啥]{.mark}

+——————————————————————————————–+
| • 核心作用：采集服务器（物理机/虚拟机）的硬件、系统资源指标（CPU、内存、磁盘、网络等） |
| |
| • 官方地址： |
| |
| https://prometheus.io/docs/guides/node-exporter/ |
| |
| • github地址： |
| |
| https://github.com/prometheus/node_exporter/ |
| |
| • 本质：Prometheus官方工具，跑在每个节点上，暴露9100端口供Prometheus抓取数据 |
+——————————————————————————————–+

1.3 安装[node-exporter]{.mark}

**步骤：**Namespace → 镜像导入 → 部署 → 验证

步骤1：创建监控专用命名空间

[root@master1 promethus]# kubectl create ns monitor-sa

namespace/monitor-sa created

步骤2：导入node-exporter镜像

node-exporter.tar.gz镜像包，必须上传到k8s所有节点（master和node都要），然后导入：

[root@xianchaomaster1 ~]# ctr -n=k8s.io images import node-exporter.tar.gz

# ⭐注意：若是docker，docker解压如下，打包则是save：

docker load -i 镜像.tar.gz  # 镜像.tar.gz换成实际文件名

# ⭐ 附录：

# 注：找镜像的方式：

# 1、拉取

docker pull prom/node-exporter:v0.16.0

# 2、导出

docker save -o  node-exporter.tar(镜像包名)  prom/node-exporter:v0.16.0（镜像）

步骤3：部署node-exporter

vim node-export.yaml （master1控制节点运行即可）

apiVersion: apps/v1

kind: DaemonSet  # 确保k8s集群的【每个节点】都运行1个相同的pod（必选，因为要采集所有节点数据）

metadata:

  name: node-exporter  # pod名称

  namespace: monitor-sa  # 放到监控专用命名空间

  labels:

    name: node-exporter

spec:

  selector:

    matchLabels:

     name: node-exporter

  template:

    metadata:

      labels:

        name: node-exporter

    spec:

      # 小白重点：3个true=让pod直接用宿主机的网络、进程、进程间通信，不用额外做端口映射

      hostPID: true    # 共享宿主机的pid（能看到宿主机所有进程）

      hostIPC: true     # 共享宿主机的ipc（进程间通信）

      hostNetwork: true  # 共享宿主机的网络（宿主机直接暴露9100端口，不用创建service）

      containers:

      - name: node-exporter

        image: prom/node-exporter:v0.16.0  # 镜像名称+版本（和导入的一致）

        imagePullPolicy: IfNotPresent  #优先用本地导入的镜像，不联网下载（避免失败）

        ports:

        - containerPort: 9100  # node-exporter默认监听端口（固定）

        resources:

          requests:

            cpu: 0.15  # 容器运行至少需要0.15核cpu（不用改）

        securityContext:

          privileged: true  # 开启特权模式（必须，否则读不到宿主机资源）

        args:  # 配置采集宿主机数据的路径，不用改

        - –path.procfs  # 读取宿主机proc目录（存放进程、系统信息）

        - /host/proc

        - –path.sysfs  # 读取宿主机sys目录（存放硬件、内核信息）

        - /host/sys

        - –collector.filesystem.ignored-mount-points  # 忽略不需要采集的目录

        - ‘“^/(sys|proc|dev|host|etc)($|/)”‘  # 正则：忽略这些目录，避免无用数据

        volumeMounts:  # 把宿主机的4个目录，挂载到容器里（必须，否则容器读不到宿主机数据）

        - name: dev

          mountPath: /host/dev  # 宿主机/dev(下面有对应) → 容器/host/dev

        - name: proc

          mountPath: /host/proc  # 宿主机/proc → 容器/host/proc

        - name: sys

          mountPath: /host/sys  # 宿主机/sys → 容器/host/sys

        - name: rootfs

          mountPath: /rootfs

      tolerations:  # 允许pod运行在master节点（master有污点，默认不让普通pod运行）

      - key: “node-role.kubernetes.io/control-plane”

        operator: “Exists”

        effect: “NoSchedule”

      volumes:  # 定义上面挂载的目录来源（都是宿主机的目录，不用改）

        - name: proc

          hostPath:

            path: /proc

        - name: dev

          hostPath:

            path: /dev

        - name: sys

          hostPath:

            path: /sys

        - name: rootfs

          hostPath:

            path: /

[⭐ 知识点]{.mark}

+:—————-+:————————————————–+:—————————————–+
| 控制器类型 | 一句话核心作用 | 典型使用场景 |
+—————–+—————————————————+——————————————+
| DaemonSet | 每个节点必跑 1 个 Pod（即每个节点都要部署组件） | 1. 节点监控（node-exporter） |
| | | |
| | | 2. 日志采集（fluentd/filebeat） |
| | | |
| | | 3. 网络插件（calico/flannel） |
+—————–+—————————————————+——————————————+
| Deployment | 按需指定副本数，支持滚动更新**（无序启停）** | 1. 业务应用（tomcat/nginx） |
| | | |
| | | 2. 普通中间件（redis/mysql 主从） |
| | | |
| | | 3. Prometheus Server（单副本 / 多副本） |
+—————–+—————————————————+——————————————+
| StatefulSet | 有状态部署（固定 Pod 名、持久化）（有序启停） | 1. 数据库集群（mysql/mongodb 集群） |
| | | |
| | | 2. 分布式存储（etcd/zookeeper） |
+—————–+—————————————————+——————————————+

2、kube-state-metrics：k8s资源状态指标采集

2.1 概念理解（kube-state-metrics）

+———————————————————————–+
| 核心作用：采集k8s资源对象状态（Pod、Node、Deployment等）， |
| |
| 比如Pod重启多少次、多少个Pod在运行 |
| |
| 注意： 只采集、不存储、数据交给Prometheus存储 |
+———————————————————————–+

2.2 安装步骤

步骤1：创建sa账号

# 创建服务账号（kube-state-metrics的访问身份）

apiVersion: v1

kind: ServiceAccount

metadata:

name: kube-state-metrics # 账号名，与组件一致

namespace: kube-system # 系统组件专用命名空间

# 创建集群角色（定义全集群只读权限）

apiVersion: rbac.authorization.k8s.io/v1

kind: ClusterRole # 集群级权限，作用于全集群

metadata:

name: kube-state-metrics # 角色名，与组件一致

rules: # 权限规则：仅允许查看（list/watch）各类资源

- apiGroups: [“”] # 核心API组（nodes/pods等基础资源）

resources: [“nodes”, “pods”, “services”, “resourcequotas”, “replicationcontrollers”, “limitranges”, “persistentvolumeclaims”, “persistentvolumes”, “namespaces”, “endpoints”]

verbs: [“list”, “watch”] # 只读：查看列表/实时监控

- apiGroups: [“extensions”] # 扩展API组（daemonsets等）

resources: [“daemonsets”, “deployments”, “replicasets”]

verbs: [“list”, “watch”]

- apiGroups: [“apps”] # 应用API组（statefulsets）

resources: [“statefulsets”]

verbs: [“list”, “watch”]

- apiGroups: [“batch”] # 批处理API组（定时任务/任务）

resources: [“cronjobs”, “jobs”]

verbs: [“list”, “watch”]

- apiGroups: [“autoscaling”] # 自动扩缩容API组

resources: [“horizontalpodautoscalers”]

verbs: [“list”, “watch”]

# 集群角色绑定（绑定账号与权限）

apiVersion: rbac.authorization.k8s.io/v1

kind: ClusterRoleBinding # 绑定集群角色到服务账号

metadata:

name: kube-state-metrics # 绑定名，与组件一致

roleRef: # 关联上面的ClusterRole

apiGroup: rbac.authorization.k8s.io

kind: ClusterRole

name: kube-state-metrics

subjects: # 关联上面的ServiceAccount

- kind: ServiceAccount

name: kube-state-metrics

namespace: kube-system # 必须与SA的命名空间一致

+—————————————————————————————————————-+
| 注： |
| |
| 1、这份配置是 kube-state-metrics 的[通用权限模板]{.mark}，可以跨集群复用； |
| |
| 2、无需修改的部分：apiGroups、resources、verbs（只读的 list/watch），kube-state-metrics 采集数据只需要这些权限 |
| |
| 3、可能需要修改的部分：所有 name 字段、namespace 字段保持一致（根据实际的名称空间、账号名字更改） |
+—————————————————————————————————————-+

# 执行创建

[root@master1 prometheus]# kubectl apply -f kube-state-metrics-rbac.yaml

clusterrole.rbac.authorization.k8s.io/kube-state-metrics created

name: kube-state-metrics

app: kube-state-metrics

  • name: kube-state-metrics

port: 8080

protocol: TCP

selector:

app: kube-state-metrics

# 注意：spec.type没有明确指定，就是默认类型ClusterIP，即集群内部访问；

prometheus-cfg.yaml文件内容注解

+———————————————————————————————————————————-+
| 一、类型 1：全局配置（global） |
| |
| ·  scrape_interval: 15s：所有任务默认 15 秒抓一次数据（核心） |
| |
| ·  scrape_timeout: 10s：抓数据超过 10 秒就放弃，避免卡壳 |
| |
| ·  evaluation_interval: 1m：暂时不用管（告警规则检查） |
| |
| [二、类型 2：服务发现（kubernetes_sd_configs）[service discovery]]{.mark} |
| |
| 作用：不用手动写节点 / 服务的 IP |
| |
| ·  role: node：只找 K8s 的节点（对应 node-exporter、cadvisor） |
| |
| ·  role: endpoints：找 K8s 的服务端点（比如 API Server、业务服务） |
| |
| ·  role: pod：找 K8s 的 Pod（比如带监控注解的业务 Pod） |
| |
| 三、类型 3：标签重写（relabel_configs） |
| |
| 作用：对自动发现的目标做 “修改 / 筛选 / 映射”，是配置里最核心的部分 |
| |
| ·  action: replace：替换内容（改地址 / 改标签） |
| |
| 例如：把节点默认的IP:10250改成IP:9100（因为 node-exporter 用 9100 端口） |
| |
| ·  action: keep：只保留符合条件的目标 |
| |
| 例如：只抓带prometheus.io/scrape: true注解的服务 / Pod，其他全过滤掉 |
| |
| ·  action: labelmap：简化标签名 |
| |
| 例如：把 K8s 自动加的长标签__meta_kubernetes_node_label_kubernetes_io_hostname简化成kubernetes_io_hostname（去掉前缀，方便看） |
| |
| [四、类型 4：采集任务（scrape_configs 下的 job_name）]{.mark} |
| |
| 作用：每个job_name对应一个 “监控任务”，专门抓一类数据 |
| |
| ⭐ 5 个任务的核心目的： |
| |
| ·  kubernetes-node：抓节点硬件数据（CPU / 内存，来自 node-exporter） |
| |
| · ** kubernetes-node-cadvisor：抓节点上的容器数据（比如容器 CPU 使用率）** |
| |
| ·  kubernetes-apiserver：抓 K8s 核心组件 API Server 的数据（看集群是否健康） |
| |
| ·  kubernetes-service-endpoints：抓 K8s Service 的数据（后续监控 Redis/Tomcat 用） |
| |
| ·  kubernetes-pods：抓 K8s Pod 的数据（后续监控业务 Pod 用） |
| |
| 五、类型 5：安全配置（tls_config/bearer_token_file） |
| |
| 关键配置： |
| |
| ca_file：K8s 的根证书（自动挂载，不用改） |
| |
| bearer_token_file：访问 K8s API 的令牌（自动挂载，不用改） |
| |
| scheme: https：用 HTTPS 访问，保证安全 |
