ConfigMap与Secret详解

一、ConfigMap详解

1.1 核心定义

+——————————————————————————+
| K8s存储非机密配置的资源对象，数据格式：key/value键值对 或 配置文件内容。 |
| |
| ⭐通俗理解：集群级“公共配置仓库”，管理明文配置（端口、域名等）。 |
+——————————————————————————+

1.2 核心作用

+——————————————————————————+
| 解决痛点：传统部署中，多服务配置分散，扩容/改配置需逐机操作，效率低。 |
| |
| 解决方案：统一管理配置，做成Volume挂载到Pod，实现“一次修改，多Pod复用”。 |
| |
| 核心逻辑： |
| |
| ConfigMap = 集群级“配置包”，可多个 |
| |
| 做成Volume后，自动映射到容器指定目录 |
| |
| 容器应用按原方式读配置，无侵入 |
+——————————————————————————+

1.3 应用场景

+———————————————————————–+
| 解耦配置与镜像：配置抽离，镜像可复用、移植性强 |
| |
| 微服务共享配置：统一存储公共配置，修改一处全服务生效 |
+———————————————————————–+

1.4 局限性

+———————————————————————–+
| 单ConfigMap数据≤1MiB，不存大文件（大文件用存储卷/数据库）。 |
| |
| 注：但是这个局限性影响不大，因为配置文件本来就是占很小的空间的 |
+———————————————————————–+

1.5 四种创建方法（精简步骤）

⭐核心命令

kubectl create configmap [名称] [参数]

# 参数可help参考

kubectl create configmap –help

1.5.1 命令行直接创建（–from-literal）[字面]

适用：配置项少（就一两行配置那种）

格式：

kubectl create configmap [名称] –from-literal=[key=value]

# 创建tomcat-config，含2个配置项

kubectl create configmap tomcat-config –from-literal=tomcat_port=8080 –from-literal=server_name=myapp.tomcat.com

# 查看

[root@master1 ~]# kubectl get cm # 简写

NAME DATA AGE

tomcat-config 2 9s

[root@master1 ~]# kubectl describe cm tomcat-config

Name: tomcat-config

Namespace: default

Labels: <none>

Annotations: <none>

Data # 数据

====

server_name: # key1

myapp.tomcat.com # key1对应的value1

tomcat_port: # key2

8080 # key2对应的value2

1.5.2 单文件创建（–from-file）[文件]

适用：完整配置文件（如nginx.conf）

格式：

kubectl create configmap [名称] –from-file=【自定义key】=【文件路径】

# 1、创建一个nginx配置文件（现在只是举例）

[root@master1 ConfigMap]# cat nginx.conf

# 2、单文件创建，指定key为www

[root@master1 ConfigMap]# kubectl create configmap www-nginx –from-file=www=./nginx.conf

1.6 三种使用方式（Pod引用）

1.6.1 环境变量引入（configMapKeyRef：配置映射）

适用：[需要把ConfigMap的某个key-value作为容器的环境变量（比如数据库连接地址、端口）。]{.mark}

# 1、创建一个存MYSQL配置的ConfigMap

[root@master1 ConfigMap]# cat mysql-testcm.yaml

apiVersion: v1

kind: ConfigMap

metadata:

name: mysql # ⭐上面的1.5.4，我们名字也是mysql，等下重新apply，会发现data就会更新为当前的数据

data:

log: “1”

lower: “1”

# 查看

[root@master1 ConfigMap]# kubectl describe cm mysql

Name: mysql

Namespace: default

Labels: <none>

Annotations: <none>

Data

====

log:

1

lower:

1

BinaryData

====

Events: <none>

# 2、创建Pod，引用上面的ConfigMap作为环境变量

[root@master1 ConfigMap]# cat mysql-pod.yaml

apiVersion: v1

kind: Pod

metadata:

name: mysql-pod

spec:

containers:

  • name: mysql

image: busybox

imagePullPolicy: IfNotPresent

command:

  • “bin/sh”

  • “-c”

  • “sleep 3600”

env: # 环境变量

  • name: log_bin

valueFrom: # 值的来源

configMapKeyRef: # 配置映射

name: mysql # 这个是configmap的名字，上面建立的名字为mysql

key: log # 这是configmap中data下key:value中的key值

  • name: lower

valueFrom:

configMapKeyRef:

name: mysql

key: lower

restartPolicy: Never

[root@master1 ConfigMap]# kubectl apply -f mysql-pod.yaml

1.6.2 方式2：通过环境变量批量引入（envFrom）

[适用场景：ConfigMap里的所有key-value都要作为环境变量，不用逐个写。]{.mark}

[root@master1 ConfigMap]# cat mysql-env.yaml

apiVersion: v1

kind: Pod

metadata:

name: mysql-pod-env # 修改下pod名

spec:

containers:

  • name: mysql

image: busybox:1.28

imagePullPolicy: IfNotPresent

command:

  • “bin/sh”

  • “-c”

  • “sleep 3600”

envFrom: # 批量引入整个ConfigMap的所有key-value作为环境变量

  • configMapRef:

name: mysql # 要引用的ConfigMap名称（还是上面的mysql）

restartPolicy: Never

# 验证

[root@master1 ConfigMap]# kubectl exec -it mysql-pod-env – /bin/sh

/ # printenv | grep low

lower=1

/ # printenv | grep log

log=1

1.6.3 ⭐方式3：做成Volume挂载（最常用，推荐）

适用：配置文件形式，支持热更新（[在不停止程序 / 服务运行的前提下，对代码、资源或配置进行更新并生效的方式）]{.mark}

# 1. 先准备ConfigMap（包含一个my.cnf配置文件）

[root@master1 ConfigMap]# cat mysql-test-configmap.yaml

apiVersion: v1

kind: ConfigMap

metadata:

name: mysql # ⭐ 记住configmap的名字，在pod中需要用到卷名

data:

log: “1”

lower: “1”

my.cnf: |

[mysqld]

welocome=Jane

# 2、创建pod，把configmap做成volume挂到容器中

[root@master1 ConfigMap]# cat mysql-pod-volume.yaml

apiVersion: v1

kind: Pod

metadata:

name: mysql-pod-volume

spec:

containers:

  • name: mysql

image: busybox

command: [“/bin/sh”,”-c”,”sleep 3600”]

volumeMounts:

  • name: mysql-config # 容器内写卷名称，其实就是volumes.name要和下面定义保持一致

mountPath: /tmp/config

volumes:

  • name: mysql-config # 与上面对应vol umeMounts对应

configMap:

name: mysql # 要引用的ConfigMap名称

restartPolicy: Never

# 3. 部署Pod

[root@xianchaomaster1 ~]# kubectl apply -f mysql-pod-volume.yaml

# 4. 验证

[root@master1 ConfigMap]# kubectl exec -it mysql-pod-volume – /bin/sh

/ # cd /tmp/config/ # 挂载目录

/tmp/config # ls

log lower my.cnf

/tmp/config # cat log

1

⭐ 相当于把ConfigMap里的每个key都变成了一个文件，文件内容就是value

1.7 ⭐ ConfigMap的热更新

环境变量方式：不自动更新，需重启Pod （即方式1和方式2：envFrom.configMapRef）

Volume方式：自动更新（约10秒延迟），无需重启 （方式3：volumes.configMap）

# 编辑ConfigMap，把log的值从1改成2

[root@master1 ConfigMap]# kubectl edit cm mysql

apiVersion: v1

data:

log: “2” # 把这里从1改成2

lower: “1”

my.cnf: |

[mysqld]

welocome=Jane

kind: ConfigMap

metadata:

annotations: # 这个单词是注释，下面的信息不用管

# 2、（等10秒左右）重新进入容器

[root@master1 ConfigMap]# kubectl exec -it mysql-pod-volume – /bin/sh

/ # cat /tmp/config/log

2/ #

二、Secret详解

2.1 核心定义

存储敏感数据（密码、私钥、token）的资源对象，与ConfigMap类似，但数据为Base64“伪加密”（可解密）

使用方式：环境变量/Volume挂载（生产常用Volume）。

2.2 3种常用类型

+———————————————————————–+
| generic/Opaque：通用类型，存密码、token（最常用） |
| |
| tls：存TLS证书/私钥 |
| |
| docker-registry：存私有Docker仓库认证信息 |
+———————————————————————–+

2.3 2种使用方式

2.3.1 环境变量引入

适用场景：敏感数据作为环境变量（比如数据库密码，应用通过读环境变量获取）。

步骤示例（创建Secret → Pod引用）：

# 1. 创建Secret（generic类型，用–from-literal指定敏感数据）

# ⭐格式，要记住【Secret名称】 、【Key值】，pod中会引用：

kubectl create secret generic【Secret名称】 –from-literal=【key】=【敏感值】

# 创建secret，记住key值为password

[root@master1 ConfigMap]# kubectl create secret generic mysql-password –from-literal=password=abcdEFG

secret/mysql-password created

# 2. 查看Secret

[root@master1 ConfigMap]# kubectl get secret

NAME TYPE DATA AGE

mysql-password Opaque 1 26s

#查看密码详细信息 （注意：value不会显示明文，只显示字节数）

[root@master1 ConfigMap]# kubectl describe secret mysql-password

Name: mysql-password

Namespace: default

Labels: <none>

Annotations: <none>

Type: Opaque

Data

====

password: 12 bytes

创建Pod，引用这个secret作为环境变量

[root@master1 secret]# cat pod-secret.yaml

apiVersion: v1

kind: Pod

metadata:

name: pod-secret

spec:

containers:

  • name: myapp

image: ikubernetes/myapp:v1

imagePullPolicy: IfNotPresent

ports:

  • containerPort: 80

env:

  • name: mysql_root_passwd # 取一个环境变量名字

valueFrom:

secretKeyRef:

name: mysql-password # 刚刚创建的【Secret名称】

key: password # 引用secret中的【key】值

[root@master1 secret]# kubectl exec -it pod-secret – /bin/sh

/ # printenv | grep pass

mysql_root_passwd=abcdEFG # 环境变量里面就能显示我们设置的密码了

2.3.2 ⭐方式2：通过Volume挂载（推荐）

适用场景：敏感数据作为文件（比如证书文件、密钥文件），应用需要读文件获取。

步骤示例（手动Base64编码 → 写YAML创建Secret → Pod挂载）：

# 创建敏感数据

# ⭐加密方式：echo -n 【原始敏感值】 | base64 （-n表示不换行，否则编码会多一个换行符）

# ⭐解密方式：echo 【加密值】 | base64 -d

# 1、用户名base64加密：YWRtaW4=

[root@master1 secret]# echo -n “admin” | base64

YWRtaW4=

# 密码base64加密：

[root@master1 secret]# echo -n “abcd1234” | base64

YWJjZDEyMzQ=

#2、创建Secret

[root@master1 secret]# cat secret.yaml

apiVersion: v1

kind: Secret

metadata:

name: mysecret

type: Opaque # 通用类型（和generic一致）

data:

username: YWRtaW4= # 加密后的用户名

password: YWJjZDEyMzQ= # 加密后的密码

# 部署及查看

[root@master1 secret]# kubectl apply -f secret.yaml

secret/mysecret created

[root@master1 secret]# kubectl get secret

NAME TYPE DATA AGE

mysecret Opaque 2 10s

创建Pod，把secret做成volume卷挂载到容器

[root@master1 secret]# cat pod_secret_volume.yaml

apiVersion: v1

kind: Pod

metadata:

name: pod-secret-volume

spec:

containers:

  • name: myapp

image: registry.cn-beijing.aliyuncs.com/google_registry/myapp:v1

imagePullPolicy: IfNotPresent

volumeMounts:

  • mountPath: /etc/secret # 容器挂载目录

name: secret-volume # 必须和定义的卷名（下面）一致

readOnly: true # 只读权限（安全，防止密码再容器内修改）

volumes:

  • name: secret-volume # 和容器里的保持一致

secret:

secretName: mysecret # 刚刚创建secret名称

# 5. 部署Pod并验证

[root@xianchaomaster1 ~]# kubectl apply -f pod_secret_volume.yaml

[root@xianchaomaster1 ~]# kubectl exec -it pod-secret-volume – /bin/sh

/ # ls /etc/secret

password username

/ # cd /etc/secret

/etc/secret # cat username # 输出admin（自动解密）

admin

/etc/secret # cat password # 输出xianchao123456f（自动解密）

abcd1234

⭐exec进入/etc/secret，cat文件可见解密后的敏感数据

三、核心区别总结

+———————–+—————————-+————————–+
| 对比项 | ConfigMap | Secret |
+———————–+—————————-+————————–+
| 存储内容 | 非敏感数据（端口、域名等） | 敏感数据（密码、私钥等） |
+———————–+—————————-+————————–+
| 数据格式 | 明文key-value/文件 | Base64伪加密key-value |
+———————–+—————————-+————————–+
| 使用推荐 | Volume挂载（支持热更新） | Volume挂载（更安全） |
+———————–+—————————-+————————–+
| 局限性 | ≤1MiB （几乎没啥影响） | 可解密，不存超高敏感数据 |
+———————–+—————————-+————————–+
