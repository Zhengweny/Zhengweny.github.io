生命周期之pod健康检测？

发表于2026-05-07|更新于2026-05-07|学习类云原生Pod
|总字数:3.3k|阅读时长:14分钟|浏览量:

1. 为什么要做健康检测？

+———————————————————————–+
| 问题场景： |
| |
| Pod 显示启动成功，但访问返回错误 |
| |
| 滚动更新时出现 404 错误 |
| |
| 应用假死但进程未退出 |
| |
| 解决方案：Kubernetes 提供三种探针机制 |
+———————————————————————–+

2. 三种探针详解

2.1 启动探测 (startupProbe)

+———————————————————————–+
| 作用：检测容器中的应用是否已经启动 |
| |
| 特点： |
| |
| 禁用其他探针，直到成功为止 （启动探针必须是先运行的） |
| |
| 失败时杀死容器并重启 |
| |
| 成功后启动其他探针 |
+———————————————————————–+

2.2 存活探测 (livenessProbe)

+———————————————————————–+
| 作用：检测容器是否正常运行 |
| |
| 特点： |
| |
| 失败时根据重启策略重启容器 |
| |
| 持续监控容器健康状态 |
+———————————————————————–+

2.3 就绪探测 (readinessProbe)

+———————————————————————–+
| 作用：检测应用是否可以接受请求 |
| |
| 特点： |
| |
| 成功后才对外提供网络访问 |
| |
| 失败时从负载均衡中移除（Service） |
+———————————————————————–+

2.4 存活探测 (livenessProbe)和 就绪探测 (readinessProbe)的区别

+———————————————————————–+
| livenessProbe（存活探测） |
| |
| 失败处理：杀死容器，根据重启策略处理 |
| |
| 影响：容器被重启 |
| |
| readinessProbe（就绪探测） |
| |
| 失败处理：从 EndPoint 列表中删除 Pod |
| |
| 影响：应用停止接收流量，但容器继续运行 |
+———————————————————————–+

3. ⭐ 探针执行顺序

+———————————————————————–+
| 启动阶段： |
| |
| startupProbe 首先执行（如果配置） |
| |
| startupProbe 成功后，livenessProbe 和 readinessProbe 并行执行 |
| |
| 注意：livenessProbe 不会等待 readinessProbe 成功 |
+———————————————————————–+

4. 三种容器健康检测方式

4.1 Exec 方式

livenessProbe: （同样可以是startupProbe或readlineProbe）

  exec:

    command:

    - cat

    - /tmp/healthy

4.2 TCP 方式（tcpSocket）

livenessProbe: （同样可以是startupProbe或readlineProbe）

tcpSocket:

port: 8080

4.3 HTTP 方式（httpGet）

livenessProbe:

httpGet:

path: /actuator/health

port: 8081

scheme: HTTP

5. 探针参数详解

1）基本参数

参数 说明 默认值 最小值

[initialDelaySeconds]{.mark} [容器启动后等待时间]{.mark} 0 0

periodSeconds 探测间隔时间 10 1

timeoutSeconds 超时时间 1 1

successThreshold 成功次数阈值 1 1

failureThreshold 失败次数阈值 3 1

2）探测结果

+———————————————————————–+
| Success：通过检测 |
| |
| Failure：未通过检测 |
| |
| Unknown：检测异常 |
+———————————————————————–+

6. 实际应用示例

6.1 startupProbe（启动探测）详细示例

1）exec模式探测（检查进程是否已启动）

[root@master1 pod_study]# cat tomcat-startupProbe.yaml

apiVersion: v1

kind: Pod

metadata:

name: tomcat-exec-startup

spec:

containers:

  • name: tomcat

image: xianchao/tomcat-8.5-jre8:v1

imagePullPolicy: IfNotPresent

ports:

  • containerPort: 8080

startupProbe: # 仅判断应用是否已启动完成

exec:

command:

  • “/bin/sh”

  • “-c”

  • “ps aux | grep [t]omcat” # ⭐以进程是否存在作为是否启动的标准，用[t]避免匹配到 grep 本身

initialDelaySeconds: 20 # 容器启动后20秒开始探测

periodSeconds: 10 # 每20秒执行一次探测

timeoutSeconds: 10 # 探测超时时间10秒

successThreshold: 1 # 成功1次就算成功

failureThreshold: 3 # 失败3次才算失败

时间线（大致）：

1、容器 Running；等待 20s。

2、第一次 exec 探测：ps aux | grep tomcat 能看到进程则判定“已启动”；否则失败计数+1。

3、每 20s 再探；连续 3 次失败则重启容器；成功后转入 liveness/readiness 并行阶段。

⭐适用于相信“主进程存在”才代表容器真正启动成功

2）httpGet模式探测（健康路由是否返回 200-399）

[root@master1 pod_study]# cat tomcat-startupProbe-httpGet.yaml

apiVersion: v1

kind: Pod

metadata:

name: tomcat-httpget-startup

spec:

containers:

  • name: tomcat

image: xianchao/tomcat-8.5-jre8:v1

imagePullPolicy: IfNotPresent

ports:

  • containerPort: 8080

startupProbe:

httpGet: # ⭐访问监控路由，返回200-399判定为“已启动”

path: / # 相当于curl http://localhost:8080/

port: 8080

initialDelaySeconds: 20

periodSeconds: 10

timeoutSeconds: 10

successThreshold: 1

failureThreshold: 3

# 观察

6.2 livenessProbe（存活性探测）详细示例

1）exec模式探测（模拟“假死”后自动重启）

⭐案例模拟了一个”假死”的应用

  • ‘touch /tmp/healthy; sleep 30; rm -rf /tmp/healthy; sleep 600’

# 解释：

1、创建健康文件：/tmp/healthy

2、等待30秒（模拟应用正常运行）

3、删除健康文件（模拟应用出现问题）

  1. 继续运行（模拟应用假死，进程还在但功能异常）

[root@master1 pod_study]# cat liveness.yaml

apiVersion: v1

kind: Pod

metadata:

name: liveness-exec

labels:

app: liveness

spec:

containers:

  • name: liveness

image: busybox:1.28

imagePullPolicy: IfNotPresent

command:

  • ‘sh’

  • ‘-c’

  • ‘touch /tmp/healthy; sleep 30; rm -rf /tmp/healthy; sleep 600’

livenessProbe:

exec:

command:

  • cat

  • /tmp/healthy

initialDelaySeconds: 10 # 容器启动后等待时间

periodSeconds: 5 # 探测间隔时间

⭐观察如下

[root@master1 pod_study]# kubectl apply -f liveness.yaml

pod/liveness-exec created

# 观察

[root@master1 ~]# kubectl get pods -w

liveness-exec 0/1 Pending 0 0s

liveness-exec 0/1 Pending 0 0s

liveness-exec 0/1 ContainerCreating 0 0s

liveness-exec 0/1 ContainerCreating 0 1s

liveness-exec 1/1 Running 0 2s

============================此时容器建立================================

liveness-exec 1/1 Running 1 (0s ago) 76s

liveness-exec 1/1 Running 2 (0s ago) 2m31s

liveness-exec 1/1 Running 3 (1s ago) 3m47s

=============================此时可以观察到大概隔75s会重启一次容器=========

# 这里可以直观的看到容器被重启几次

[root@master1 pod_study]# kubectl get pods

NAME READY STATUS RESTARTS AGE

liveness-exec 1/1 Running 2 (30s ago) 3m1s

计算：

0-30秒：应用正常

30-40秒： （initialDelaySeconds）容器启动后等待10秒之后进入探测

40-45秒：（periodSeconds）间隔5秒进行探测，此时第一次发现应用异常

45-60秒：第二次探测发现应用异常（initialDelaySeconds+periodSeconds=15s）

60-75秒：第3次探测发现应用异常，默认连续3次失败触发重启，因此是75秒

# 查看事件

[root@master1 ~]# kubectl get events -w

8m33s Normal Created pod/liveness-exec Created container liveness

8m33s Normal Started pod/liveness-exec Started container liveness

# 可以看到对应时间，确实执行了cat /tmp/healthy文件然后找不到

6m43s Warning Unhealthy pod/liveness-exec Liveness probe failed: cat: can’t open ‘/tmp/healthy’: No such file or directory

9m3s Normal Killing pod/liveness-exec Container liveness failed liveness probe, will be restarted

2）httpGet模式探测（模拟“假死”后自动重启）

⭐案例意图：

真实应用场景：SpringBoot 应用的健康检查

HTTP 探针配置：如何检测 Web 应用

# 先在两个node节点上，导入springboot镜像

[root@node1 pod_study]# ctr -n=k8s.io image import springboot.tar.gz

[root@node2 pod_study]# ctr -n=k8s.io image import springboot.tar.gz

[root@master1 pod_study]# cat liveness-http.yaml

apiVersion: v1

kind: Pod

metadata:

name: liveness-http

labels:

app: v1

spec:

containers:

  • name: liveness-http

image: mydlqclub/springboot-helloworld:0.0.1

imagePullPolicy: IfNotPresent

livenessProbe:

httpGet:

scheme: HTTP

path: /actuator/health

port: 8081

initialDelaySeconds: 20 # 延迟20秒开始探测

periodSeconds: 5 # 每5秒探测一次

timeoutSeconds: 10 # 超时时间10秒

⭐执行如下

1、容器启动：SpringBoot应用开始启动

2、等待阶段：等待20秒（initialDelaySeconds）

3、第一次探测：发送HTTP GET请求到http://容器IP:8081/actuator/health

⭐如果返回200-399状态码，探测成功

⭐如果返回其他状态码或连接超时，探测失败

4、后续探测：每5秒重复探测

5、失败处理：连续3次失败后，容器被杀死并重启

3）tcpSocket模式探测（端口不通即重启）

[root@master1 pod_study]# cat liveness-tcpSocket.yaml

livenessProbe:

tcpSocket:

#host: localhost # ⭐这里有个坑，tcpSocket一般是不用指定host的，测试中我加入了localhost，导致容器一直重启

port: 8081

6.3 readinessProbe（就绪探测，与 Service 配合，控制是否接流量，对外提供服务）

⭐示例场景：

以 SpringBoot 项目为例，通过 ReadinessProbe 探测项目的 8081 端口下的 /actuator/health 接口：

1、探测成功：代表应用启动完成，开放对外访问；

2、探测失败：应用未就绪，暂不对外提供服务，直至探测成功。

[root@master1 pod_study]# vim readiness-exec.yaml

# 服务定义（四层代理，关联后端 Pod）

apiVersion: v1

kind: Service

metadata:

name: springboot

labels:

app: springboot

spec:

type: NodePort # 暴露端口到节点

ports:

  • name: server # 应用服务端口

port: 8080 # Service 端口

targetPort: 8080 # 容器内应用端口

nodePort: 31180 # 节点映射端口

  • name: management # 健康检查端口

port: 8081 # Service 端口

targetPort: 8081 # 容器内健康检查端口

nodePort: 31181 # 节点映射端口

selector: # ⭐ 关联标签为 app:springboot 的 Pod

app: springboot

# Pod 定义（包含 ReadinessProbe 配置）

apiVersion: v1

kind: Pod

metadata:

name: springboot （⭐下面http探测成功之后，service的selector会关联到pod,）

labels:

app: springboot

spec:

containers:

  • name: springboot

image: mydlqclub/springboot-helloworld:0.0.1

imagePullPolicy: IfNotPresent # 本地有镜像则不拉取

ports:

  • name: server

containerPort: 8080 # 应用服务端口

  • name: management

containerPort: 8081 # 健康检查端口

readinessProbe: # 就绪探针配置

initialDelaySeconds: 20 # 容器启动后，延迟 20 秒开始首次探测

periodSeconds: 5 # 探测间隔（每 5 秒一次），连续两次成功视为就绪

timeoutSeconds: 10 # 探测超时时间（10 秒未响应则视为失败）

httpGet: # 使用 HTTP 方式探测

scheme: HTTP # 协议（HTTP/HTTPS）

port: 8081 # 目标端口（健康检查端口）

path: /actuator/health # 探测路径（健康检查接口）

⭐ Service 通过 selector 关联 Pod，仅当 Pod 的 ReadinessProbe 探测成功后，Service 才会将流量转发至该 Pod；

6.4 生产环境推荐：先启动、再并行就绪+存活

apiVersion: v1

kind: Service

metadata:

  name: springboot-live

  labels:

    app: springboot

spec:

  type: NodePort # 负载均衡中流量路由的方式，以下用端口的方式匹配

  ports:

  - name: server

    port: 8080 # ⭐必填项，pod中服务对应的端口

    targetPort: 8080 # 表示目的要找哪个端口去映射

    nodePort: 31180 # 对应服务在节点上暴露的端口

  - name: management

    port: 8081

    targetPort: 8081

    nodePort: 31181

  selector: # 选择器，匹配pod的标签

    app: springboot

apiVersion: v1

kind: Pod

metadata:

  name: springboot-live

  labels:

    app: springboot

spec:

  containers:

  - name: springboot

    image: mydlqclub/springboot-helloworld:0.0.1

    imagePullPolicy: IfNotPresent

    ports:

    - name: server

      containerPort: 8080

    - name: management

      containerPort: 8081

    startupProbe:             # 【判断应用是否启动完成】冷启动阶段只跑它；成功前不会启动 liveness/readiness

      initialDelaySeconds: 20

      periodSeconds: 5

      timeoutSeconds: 10

      httpGet:

        scheme: HTTP

        port: 8081

        path: /actuator/health

    readinessProbe:               # 【应用能否接收请求】能接流量的条件；失败只摘流量（service），不重启

      initialDelaySeconds: 20

      periodSeconds: 5

      timeoutSeconds: 10

      httpGet:

        scheme: HTTP

        port: 8081

        path: /actuator/health

    livenessProbe:               # 【应用是不是”假死”】运行期兜底自愈；失败触发重启

      initialDelaySeconds: 20

      periodSeconds: 5

      timeoutSeconds: 10

      httpGet:

        scheme: HTTP

        port: 8081

        path: /actuator/health

6.5 ⭐总结

1、3 种核心探针：功能与区别

+————————————-+——————————————–+—————————————————————+——————————————————————+
| [探针类型]{.mark} | [核心作用]{.mark} | [探测失败处置]{.mark} | [优先级 / 执行顺序]{.mark} |
+————————————-+——————————————–+—————————————————————+——————————————————————+
| [startupProbe（启动探测）]{.mark} | [检测应用是否 “启动完成”]{.mark} | [杀死容器，按重启策略重启]{.mark} | [最高，成功后才执行另外两种探针；未配置则默认 “成功”]{.mark} |
+————————————-+——————————————–+—————————————————————+——————————————————————+
| [livenessProbe（存活探测）]{.mark} | [检测应用是否 “正常运行”（无假死）]{.mark} | [杀死容器，按重启策略重启]{.mark} | [与就绪探针并行（不等待就绪探针成功）；未配置默认 “成功”]{.mark} |
+————————————-+——————————————–+—————————————————————+——————————————————————+
| [readinessProbe（就绪探测）]{.mark} | [检测应用是否 “可接收请求”]{.mark} | [将 Pod 从 Service 的 Endpoint 移除（不对外提供服务）]{.mark} | 与存活探针并行；未配置默认 “成功” |
+————————————-+——————————————–+—————————————————————+——————————————————————+

2、探针的 3 种探测方式（通用）

+————————————————————————————————————————————–+
| [所有探针（启动、存活、就绪）均支持以下 3 种检测逻辑，按需选择：]{.mark} |
| |
| exec：在容器内执行命令，退出码为 0 则成功（例：[cat /tmp/healthy]{.mark}检测文件是否存在）； |
| |
| TCPSocket：尝试与容器的 IP + 端口建立 TCP 连接，连接成功则成功（例：检测 Nginx 的 80 端口）； |
| |
| HTTPGet：向容器的 IP + 端口 + 路径发送 HTTP GET 请求，响应码 200-399 则成功（例：检测 SpringBoot 的[/actuator/health]{.mark}接口）。 |
+————————————————————————————————————————————–+

3、探针关键配置属性（通用）

+———————————————————————————————–+
| initialDelaySeconds：容器启动后，延迟多久开始探测（例：20 秒，避免应用未启动就误判）； |
| |
| periodSeconds：探测间隔时间（默认 10 秒，例：5 秒一次高频检测）； |
| |
| timeoutSeconds：探测请求超时时间（默认 1 秒，例：10 秒适配慢接口）； |
| |
| successThreshold：连续探测成功多少次算 “真成功”（存活探针必须为 1，默认 1）； |
| |
| failureThreshold：连续探测失败多少次算 “真失败”（默认 3 次，例：3 次失败后重启 / 移除服务）。 |
+———————————————————————————————–+
