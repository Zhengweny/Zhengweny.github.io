一、K8s为什么要做持久化存储？

+——————————————————————————–+
| 核心原因：Pod有生命周期，数据会随Pod删除/重启丢失 |
| |
| **持久化存储：**把数据存到独立于Pod的地方，让数据长久保留，不受Pod生命周期影响 |
+——————————————————————————–+

二、K8s存储卷怎么用？

2.1 查看K8s支持的存储类型

# kubectl explain pods.spec.volumes

常见的有：emptyDir、hostPath、nfs等

2.2 ⭐存储卷使用两步法

+—————————————————————————————————-+
| 定义Pod的Volume：告诉K8s这个Volume要关联到哪种存储（比如emptyDir、NFS） |
| |
| 容器内挂载（volumeMounts）：告诉容器把这个Volume挂载到自己的哪个目录下，这样容器就能使用存储了 |
+—————————————————————————————————-+

三、常用存储类型详解

3.1 临时存储：emptyDir（用完即删，适合临时场景）

3.1.1 核心特点

+————————————————————————-+
| Pod调度到Node时自动创建，Node上会生成一个空目录，不用手动指定宿主机目录 |
| |
| Pod从Node上移除（如删除、调度走），emptyDir里的数据永久删除 |
| |
| 适用场景：临时缓存、同一个Pod内多个容器共享文件 |
+————————————————————————-+

3.1.2 实操步骤：创建挂载emptyDir的Pod

[root@master1 volume]# cat emptydir.yaml

metadata:

name: pod-empty

spec:

3.2 节点级存储：hostPath（挂宿主机目录，单节点可用）

3.2.1 核心特点

+——————————————————————————-+
| 把Pod所在宿主机的某个目录/文件挂载到容器里 |
| |
| Pod删除后，宿主机目录还在，数据不会丢 |
| |
| 致命缺点：Pod重新创建后必须调度到同一个Node才能用之前的数据，不支持跨节点 |
| |
| 适用场景：单节点测试，不适合生产集群 |
+——————————————————————————-+

3.2.2 实操步骤：创建挂载hostPath的Pod

# 把tomcat镜像传到所有Node节点

3.3 ⭐网络存储：NFS（跨节点共享，集群常用）

3.3.1 核心特点

+—————————————————————————————————————+
| NFS是网络文件系统，有一个**”服务器”共享目录**，所有Node节点（也就相当于每台服务器嘛）都能通过网络挂载这个目录 |
| |
| Pod无论调度到哪个Node，只要挂载NFS，就能访问到同一个共享目录，支持跨节点数据共享 |
| |
| 缺点：NFS服务器单点故障（宕机了所有Pod都用不了数据），生产做高可用更好 |
| |
| 适用场景：K8s集群跨节点数据共享，如多Pod共用配置文件、静态资源 |
+—————————————————————————————————————+

3.3.2 实操步骤：搭建NFS并挂载

步骤1：⭐搭建NFS服务器（实验用了master节点当nfs服务端）

# 安装nfs服务

[root@master1 volume]# yum install -y nfs-utils

# 创建nfs共享目录

# pv是参数：-p 表示父级目录（/data）不存在时,会先创建父级目录，再创建下面的volumes;-v表示详细模式

[root@master1 volume]# mkdir /data/volumes -pv

# 配置nfs共享规则（/etc/exports 不是export!!!!）→ 指定共享目录和权限

[root@master1 volume]# cat /etc/exports

3.4 ⭐集群级存储：PVC/PV（生产核心）

3.4.1 核心问题：为什么需要PVC/PV？

+————————————————————————————+
| 没有 PVC/PV：开发者要懂存储底层细节，容易错、权限乱； |
| |
| 有了 PVC/PV：管理员管存储（PV），开发者提需求（PVC），双方隔离，改存储不用动 Pod； |
| |
| 核心就是 “分工明确”，把存储的管理（PV）和使用（PVC）拆开来。 |
+————————————————————————————+

3.4.2 核心概念

概念 角色 通俗理解

PV（PersistentVolume，持久卷） 集群资源，管理员创建 相当于“仓库”，管理员提前把存储（如NFS、Ceph）做成一个个PV，放在集群里供使用，生命周期独立于Pod

PVC（PersistentVolumeClaim，持久卷声明） 资源请求，开发者创建 相当于“领料单”，开发者不用管仓库在哪，只写清楚要多大空间、能怎么访问（读/写），K8s自动匹配合适的PV

3.4.3 工作原理：PV与PVC的生命周期

[1、供应：管理员建 PV（填存储类型 / 大小 / 规则），要么手动建（静态），要么 K8s 按需自动建（动态，用 StorageClass）]{.mark}

[2、绑定：开发者建 PVC 提需求（如 1G / 读写），K8s 找匹配的 PV 绑定，绑定后 PV 只能给这个 PVC 用；]{.mark}

[3、使用：Pod 挂载 PVC 名就能用存储，数据存在 PV 对应的存储（如你的 NFS 目录）；]{.mark}

[4、回收：删 Pod 不影响 PVC/PV，删 PVC 后 PV 按规则处理（默认 Retain：保留数据但需手动重置；Delete：删 PV + 底层存储，慎用，但经过测试，其实底层数据并不会丢）。]{.mark}

[⭐⭐注意：]{.mark}

PV 和 PVC 的关系 → 严格一对一

PVC 和 Pod 的关系 → 可以一对多

3.4.4 关键配置：访问模式

PVC和PV的访问模式必须匹配，否则绑定失败。3种核心模式

简称 全称 含义 支持的存储举例

RWO ReadWriteOnce 单节点读写：只能被一个节点上的Pod读写 hostPath、Ceph

ROX ReadOnlyMany 多节点只读：多个节点的Pod都能读，不能写 NFS、GlusterFS

RWX ReadWriteMany 多节点读写：多个节点的Pod都能读写（最灵活） NFS、GlusterFS

⭐注意：

1、动态 PV（StorageClass 创建）：

Delete 策略会真正删除底层存储（如 AWS EBS 卷、阿里云云盘），数据 100% 消失；

2、静态 PV（手动创建），即测试的这种：

若 PV 指向本地目录 / NFS 路径，Delete 策略仅删除 PV 对象，底层目录 / 文件可能仍存在（取决于存储插件实现），但 K8s 不再管理，不建议依赖。

3.4.6 关键注意事项（避坑指南）

+——————————————————————————————————————————–+
| PVC和PV绑定条件：PVC的存储需求一定是小于等于PV存储的， 不能超过，否则PVC一直Pending； |
| |
| 删除顺序：必须先删除使用PVC的Pod，再删除PVC，否则删不了PVC； |
| |
| Retain策略复用：删除PVC后，PV处于Released状态，要复用需手动删除PV（kubectl delete pv 名字），重新创建PVC会再次绑定，数据不丢； |
| |
| 动态供应：生产中常用StorageClass实现动态PV创建，不用管理员手动建PV，PVC创建时自动生成对应PV，更高效。 |
+——————————————————————————————————————————–+

四、三种存储类型对比

+————-+———————————-+——————————+—————————+———————————-+————————+—————————–+
| 存储类型 | 数据持久化 | 跨节点共享 | 适用场景 | 优点 | 缺点 | 维护成本 |
+————-+———————————-+——————————+—————————+———————————-+————————+—————————–+
| emptyDir | Pod删除则丢失 | 不支持 | 临时缓存、Pod内多容器共享 | 无需配置，自动创建 | 数据不持久 | 无 |
+————-+———————————-+——————————+—————————+———————————-+————————+—————————–+
| hostPath | 宿主机目录（node节点）存在则不丢 | 不支持（需调度到同个Node） | 单节点测试 | 配置简单，数据单节点持久 | 不支持跨节点，集群无用 | 低 |
+————-+———————————-+——————————+—————————+———————————-+————————+—————————–+
| NFS | NFS服务器正常则不丢 | 支持 | 集群跨节点共享数据 | 跨节点共享，配置不复杂 | 服务器单点故障风险 | 中（需维护NFS服务器） |
+————-+———————————-+——————————+—————————+———————————-+————————+—————————–+
| PVC/PV | 取决于底层存储（如NFS/Ceph） | 取决于底层存储（如NFS/Ceph） | 支持（取决于底层存储） | 解耦管理，灵活扩展，适配多种存储 | 大规模生产环境 | 中高（需规划PV/PVC/存储类） |
+————-+———————————-+——————————+—————————+———————————-+————————+—————————–+

五、⭐总结

+———————————————————————————————————-+
| 1、PV=存储盘 （涉及用什么存储nfd、gfs等等，回收策略等） |
| |
| 2、PVC=存储需要（我要申请什么存储盘） |
| |
| 3、测试环境：emptyDir（临时）、hostPath（单节点）、NFS（跨节点）； |
| |
| 4、生产环境：PVC/PV + 分布式存储（CephFS/GlusterFS），配合StorageClass实现动态供应，兼顾高可用和灵活性； |
+———————————————————————————————————-+
